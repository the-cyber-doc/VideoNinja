# Video Ninja

Installable web app (PWA) for Ninjutsu technique videos, organised as each
school teaches them: school (ryu) → category (Taijutsu, Muto Dori, Buki) →
weapon (under Buki) → scroll or form (e.g. Jo Ryaku no Maki) → technique →
video segments, with annotations.
Self-hosted on a Raspberry Pi 5 with Docker behind nginx.

## Layout

| Path | Content |
|---|---|
| `server/app/` | Backend: Python 3.15 + FastAPI. `main.py` assembles it from `api/` (the HTTP endpoints, one router per module), `domain/` (the rules: sessions, invitations, annotations, catalogue snapshots, the audit log…), `queries/` (every SQL statement, one module per table), `core/` (settings, logs, errors, database connection and migrations, time, encryption, processes) and `encoder/` (the encoding queue, its own container in production) |
| `server/tests/` | Backend tests (pytest) |
| `server/pyproject.toml` | Settings of the backend's development tools: Ruff (lint, format), mypy, coverage |

| `server/database/catalog/techniques.json`, `tools/catalog-sql.py` | The schools' techniques (source) and the generator of their block in the newest `db_v<N>_init.sql` (see [The catalogue of techniques](#the-catalogue-of-techniques)) |
| `frontend/` | SvelteKit PWA (`adapter-static`, Svelte 5, TypeScript) |
| `frontend/src/**/*.test.ts` | Frontend unit tests (Vitest) |
| `frontend/tests/` | Browser tests (Playwright): `mocked/` (fake API), `pwa/` (service worker), `e2e/` (real backend) |
| `frontend/src/service-worker/` | PWA service worker (offline shell, catalogue cache) |
| `frontend/static/` | Files served as is: `manifest.webmanifest`, `icons/` (generated by `npm run icons`) |
| `server/app/validation.json` | Input rules (lengths, patterns) shared by backend and frontend |
| `server/openapi.json`, `frontend/src/lib/api/schema.d.ts`, `tools/api-types.sh` | The API's OpenAPI schema and the frontend's TypeScript types generated from it (see [API types](#api-types)) |
| `nginx/nginx.conf` | The nginx container's configuration (see [6. Reverse proxy and nginx](#6-reverse-proxy-and-nginx)) |
| `server/Dockerfile` | The four images (`--target nginx`, `api`, `encoder`, `tusd`) |
| `tools/encode-videos/` | `encode-videos.sh` (ffmpeg H.265 encoding) + NNEDI3 weights, used by the server's encoding queue |
| `docker-compose.dev.yaml`, `tools/docker-dev.sh` | The production images built from the checkout and run locally on the development data (see [9. Docker images](#9-docker-images)) |
| `tools/make-dev-db.py` | A development database with a fixed test admin (see [Test admin without the wizard](#test-admin-without-the-wizard)) |

| `tools/test-e2e-stack.sh` | The e2e tests against the four real containers, on a throwaway instance (see [End-to-end tests on the containers](#end-to-end-tests-on-the-containers)) |
| `.github/workflows/ci-cd.yml` | CI: tests + builds on every push; images published only for `v*` tags |

#### Installing tusd

tusd is a single binary, installed for your user only (no sudo). The backend
finds it on `PATH`, or at `VIDEONINJA_TUSD_BIN`. The checksum is the one
published with the release (also pinned in `server/Dockerfile`):

```bash
# amd64 (most PCs). On arm64 (Raspberry Pi, Apple silicon Linux VMs) use the
# second ARCH/SHA line instead.
ARCH=amd64 SHA=e8c8d7738275d2d9377db953aecbc242262d3620e77fbd3c1491361d9cea6ac8
# ARCH=arm64 SHA=134e575a6524698b54d989958c680f0a4ec243d9622c1926e30e27c2a86e4752

cd "$(mktemp -d)"
curl -sSLO "https://github.com/tus/tusd/releases/download/v2.10.1/tusd_linux_$ARCH.tar.gz"
echo "$SHA  tusd_linux_$ARCH.tar.gz" | sha256sum -c     # must print: OK
tar -xzf "tusd_linux_$ARCH.tar.gz"
mkdir -p ~/.local/bin && mv "tusd_linux_$ARCH/tusd" ~/.local/bin/
tusd -version                                        # Version: v2.10.1
```

If `tusd -version` is not found, add `~/.local/bin` to `PATH` (e.g.
`export PATH="$HOME/.local/bin:$PATH"` in `~/.bashrc`), then open a new
terminal.

### 1. Get the code

```bash
git clone git@github.com:the-cyber-doc/VideoNinja.git
cd VideoNinja
```

Everything happens on `main`, for development and releases. Commit to `main`
directly, or use a short-lived feature branch and a pull request to `main`.

Every push, on any branch, runs CI: backend tests, frontend type-check and
build, and the Docker image build for amd64 and arm64. Nothing is published.
Keep `main` green. Users only get what is released with a tag (see
[Releasing](#releasing)).

### 2. Backend (terminal 1)

```bash
cd server
# uv downloads Python 3.15 if needed; --seed puts pip in the venv.
# (With a system Python 3.15: python3.15 -m venv .venv)
uv venv --python 3.15 --seed .venv
. .venv/bin/activate
pip install --require-hashes -r requirements-dev.txt

# Encryption key for development (32 random bytes, base64). Never commit it.
python -c "import base64, os; print(base64.b64encode(os.urandom(32)).decode())" > dev.key

VIDEONINJA_DB=dev.db VIDEONINJA_DB_KEY_FILE=dev.key uvicorn app.main:app --reload
```

The API listens on `http://localhost:8000`. `dev.db`, `dev.key` and the
catalogue snapshots in `catalog/` are ignored by git.

Git hooks (once, after the frontend's `npm ci` too): `server/.venv/bin/pre-commit install`
in the repository. Each commit then checks its staged files with the tools of
`server/.venv` and `frontend/node_modules` (`.pre-commit-config.yaml`; nothing
downloaded): no large files or private keys, whitespace, Ruff, mypy, Prettier,
ESLint. The formatters fix the files themselves: `git add` them and commit again.
`server/.venv/bin/pre-commit run --all-files` checks everything.

Every setting is read and checked at startup (`server/app/core/settings.py`): a wrong
value stops the API or the encoder, and the error names every wrong variable at
once.

| Variable | Default | Purpose |
|---|---|---|
| `VIDEONINJA_DB` | `/data/videoninja.db` | SQLite database file. If missing, the app starts in setup mode. |
| `VIDEONINJA_DB_KEY_FILE` | `/run/secrets/videoninja_key` | Key that encrypts the TOTP secrets in the database. The app does not start without it. |
| `VIDEONINJA_DB_KEY` | unset | The key itself (base64), instead of a file. Setting it together with `VIDEONINJA_DB_KEY_FILE` refuses the start. The app removes it from its environment once read, so the tools it runs (tusd in development, brotli, zopfli) don't inherit it. Prefer the file (Docker secret): a variable shows in `docker inspect`. |
| `VIDEONINJA_CATALOG_DIR` | `catalog/` next to the database (image: `/srv/catalog`) | Catalogue snapshots (static JSON files, see [Catalogue updates](#catalogue-updates)). |
| `VIDEONINJA_X_ACCEL` | unset (image: `1`) | `1`: behind nginx, `/api/catalog` answers with `X-Accel-Redirect` and nginx sends the file. Unset: the app sends the file itself (development, no nginx). |
| `VIDEONINJA_MEDIA_DIR` | `media/` next to the database (image: `/srv/media`) | Encoded videos and thumbnails (`video/<h2>/<sha256>/…`), written by the encoding queue. Without nginx the app serves the thumbnails from here. |
| `VIDEONINJA_UPLOAD_DIR` | `uploads/` next to the database (image: `/srv/uploads`) | tusd's folder: originals waiting to be encoded. |
| `VIDEONINJA_MAX_UPLOAD_BYTES` | `21474836480` (20 GiB) | Largest upload accepted (the app's tusd hook; tusd's `-max-size` gets the same value). The upload page refuses a larger file at once. |
| `VIDEONINJA_INPUT_FORMATS` | `mov,matroska,avi,mpegts,mpeg,dv,asf` | The ffmpeg demuxers allowed for uploads (`-format_whitelist`): MP4/MOV/M4V/3GP, MKV/WebM, AVI, MTS/M2TS/TS, MPG/VOB, DV, WMV. They also give the file extensions the upload page and tusd's hook accept. Any other name stops the start. |
| `VIDEONINJA_FFMPEG_TIMEOUT_H` | `24` | Each ffmpeg run (and a whole encoding) is stopped after this many hours: the video fails, it is not tried again. |
| `VIDEONINJA_FFPROBE_TIMEOUT_MIN` | `10` | The same for each ffprobe run, in minutes: it only reads the file's headers and index. |
| `VIDEONINJA_ARGON2_CONCURRENCY` | `2` | Password checks (Argon2: 64 MiB and a CPU core each) running at once; the others wait up to 10 s, then get `503` with `Retry-After` ("the server is busy"). |
| `VIDEONINJA_X265_PRESET` | `medium` | libx265 preset of the encoding queue (`ultrafast` … `veryslow`; slower = smaller files). Case, spaces and quotes are ignored; any other value stops the app at start, naming the value received. |
| `VIDEONINJA_LOG_LEVEL` | `INFO` | `DEBUG`, `INFO`, `WARNING` or `ERROR`, for the app and uvicorn (API and encoder). `DEBUG` adds tusd's own output in development. |
| `VIDEONINJA_LOG_FORMAT` | `text` (images: `json`) | `text`: one readable line per message (`12:13:38 INFO     app.encoder.queue: …`). `json`: one JSON object per line (`ts`, `level`, `logger`, `msg`, and `exc` with the traceback), for `journalctl` and `jq`. Every line of a request carries its `request_id` (nginx's `$request_id`: `rid=` in nginx's log, `X-Request-ID` in the answer) and, once the session is checked, `user_id`; the encoder's lines of a video carry `video_id`. The app logs one line per request (`app.middleware`: method, route template, status, `duration_ms`; a healthy `/health` only at `DEBUG`) instead of uvicorn's access log. Any other value of either stops the start. |
| `TZ` | system timezone (image: UTC) | Server's timezone (IANA name, e.g. `Europe/Zurich`), for dates written without a user: invitations. Users' dates are in their browser's timezone. |
| `VIDEONINJA_BASE_PATH` | `''` (image: `/videoninja`) | Where the browser sees the app (a subfolder of the domain). The session cookie's name and path and tusd's upload URLs follow it; the frontend is built with the same value (`BASE_PATH`). |
| `VIDEONINJA_TUSD` / `VIDEONINJA_ENCODER` | on (api image: `0`) | `0`: don't start tusd / the encoding thread in the app (their own containers in production; tests). tusd also needs the binary (`PATH` or `VIDEONINJA_TUSD_BIN`), encoding needs `ffmpeg`. |
| `VIDEONINJA_TUSD_HOST` / `VIDEONINJA_TUSD_PORT` | `127.0.0.1` / `1080` | Where the tusd the app runs itself (development) listens. |
| `VIDEONINJA_APP_PORT` | `8000` | The app's port, where that tusd calls its hooks. |
| `VIDEONINJA_ENCODE_SCRIPT` | `tools/encode-videos/encode-videos.sh` of the repository (encoder image: `/app/encode/encode-videos.sh`) | The encoding script the queue runs. |
| `VIDEONINJA_TUSD_URL` | unset (api image: `http://tusd:1080`) | tusd in another container: the app checks that it answers (`/health`, the upload page's warning). |
| `VIDEONINJA_API_URL` | unset (encoder image: `http://api:8000`) | The encoder in its own container: where it asks for a catalogue rebuild after publishing a video or making thumbnails. Unset: it runs in the app and rebuilds directly. |

### 3. Frontend (terminal 2)

SvelteKit needs Node.js ≥ 22.17; distribution packages are often older
(`npm ci` then fails with `EBADENGINE`). Install Node.js 26 in your home
directory with [fnm](https://github.com/Schniz/fnm), no sudo needed:

```bash
curl -fsSL https://fnm.vercel.app/install | bash
exec $SHELL                 # reload the shell so fnm is on PATH
fnm install 26
fnm default 26
node --version              # v26.x
```

[nvm](https://github.com/nvm-sh/nvm) works too (`nvm install 24 && nvm alias default 24`).
A system Node.js can stay installed: fnm's comes first on `PATH`.

```bash
cd frontend
npm ci
npm run dev
```

Open **https://localhost:5173** and accept the self-signed certificate once.
The dev server runs over HTTPS because the session cookie is `Secure`, as in
production. It forwards `/api` to the backend on port 8000.

### 4. First start

With no database, the backend prints a one-time setup token in terminal 1:

```
12:13:38 WARNING  app.api.setup: Video Ninja is not set up yet. Setup token: 3q2-…
```

The app opens the setup wizard: enter the token, create the admin account
(password + authenticator app), and the database is built. Then log in.

To start over, stop the backend and delete `server/dev.db` (and
`dev.db-wal` / `dev.db-shm` if present) and `server/catalog/`.

#### Test admin without the wizard

`tools/make-dev-db.py` builds the database outside the app, like the wizard
does (the latest `db_vN.sql` + `db_vN_init.sql`), with an admin whose
credentials are fixed in the script: add its TOTP secret to your
authenticator once, and every rebuilt database logs in the same way.

```bash
# From the repository root, the backend stopped. Key: server/dev.key (required).
server/.venv/bin/python tools/make-dev-db.py            # creates server/dev.db
server/.venv/bin/python tools/make-dev-db.py --force    # replaces it (and its -wal/-shm)
```

| Variable in the script | Value |
|---|---|
| `USERNAME` | `admin` |
| `PASSWORD` | `XhvqKL3zKA7S` |
| `TOTP_SECRET` | `J3BFCBSLVAZSG3M7POCBI235XUL35XUQ` (base32; `oathtool --totp -b <secret>` prints the current code) |

Change them in the script; it checks them against `server/app/validation.json`.
These credentials are public: use such a database for development and test
instances only, never in production. The catalogue snapshot is rebuilt at the
backend's next start. `--db` and `--key` choose other files.

For a test instance on the Raspberry Pi (fresh install, before its first
start), build the database on your machine with the Pi's key, then copy it
into the container's `data` volume, owned by the container's user:

```bash
# On your machine: the Pi's key (from /opt/videoninja/.env) in a temporary file
umask 077; echo '<the base64 key>' > pi.key
server/.venv/bin/python tools/make-dev-db.py --db videoninja.db --key pi.key
rm pi.key
# On the Pi, in /opt/videoninja, with videoninja.db copied there:
sudo chown 10001:10001 videoninja.db
sudo docker compose create
sudo docker compose cp -a videoninja.db server:/data/videoninja.db
sudo docker compose up -d && sudo rm videoninja.db
```

### 6. Frontend tests

Two levels, both run by CI on every push:

| Command | Tool | What | Speed |
|---|---|---|---|
| `npm run test:unit` | [Vitest](https://vitest.dev) | Plain functions, files `src/**/*.test.ts` next to the code | milliseconds |
| `npm run test:browser` | [Playwright](https://playwright.dev) | Pages in real browsers, files in `tests/` | seconds |

`npm test` runs both. `npm run test:coverage` (CI) runs the unit tests with
coverage of `src/**/*.ts`: every module, the service worker included, at 100% of
its statements and lines and 99% of its branches and functions (floors in
`vite.config.ts`). The browser APIs these modules use (Cache API, IndexedDB,
the service worker's scope, video elements) are faked in `src/lib/testing/`.
Components (`.svelte`) are the browser tests' (no coverage measured there).

Browser tests come in two kinds:

- **`tests/mocked/`**: the API is faked with `page.route`, no backend needed.
  For page behaviour and error cases that are hard to produce for real. Run
  in Chromium and WebKit (Safari's engine).
- **`tests/pwa/`**: the service worker on the production build: manifest and
  icons, offline start with the cached catalogue, catalogue update, caches
  cleared on logout. The API is faked with `context.route` (`page.route` does
  not see the service worker's requests; the mocked tests block the service
  worker for that reason). Chromium only.
- **`tests/e2e/`**: full flows against the real backend (setup → login →
  logout → profile: name, password, authenticator). Playwright starts a fresh backend on port 8001
  (`tests/e2e/backend.sh`: new database and key in `frontend/.e2e/`, setup
  token read from `.e2e/server.log`), so a dev backend on 8000 is not
  affected. Chromium only; the tests run in order.

Playwright also builds the app (every run) and serves it with `vite preview`
on `https://localhost:4183`, not 4173, so a preview you started yourself is
never mistaken for the test build. The e2e backend needs the backend's virtual
environment (`server/.venv`, see [Backend](#2-backend-terminal-1)), or another
Python with the dependencies in `PYTHON`.

First run, in `frontend/`:

```bash
npx playwright install chromium webkit   # browsers, in ~/.cache/ms-playwright
npm run test:browser
```

Useful options:

```bash
npx playwright test --project chromium --project pwa --project e2e   # skip WebKit
npx playwright test --ui              # interactive: step through, see each action
npx playwright test --headed          # watch the browser
npx playwright codegen https://localhost:4173   # record clicks as test code (your own preview)
```

WebKit needs system libraries (`sudo npx playwright install-deps webkit`).
Playwright officially supports Ubuntu 22.04 and 24.04 LTS. On other
distributions WebKit may not start: on Ubuntu 25.10, for example, its build
for 24.04 needs `libicu74` and `libxml2.so.2`, which apt cannot install there
(25.10 has `libicu76` and `libxml2.so.16`), so `install-deps` does not help.

There, and in general for one run of every browser test with the same
browsers and system libraries as CI, run the browsers in Playwright's own Docker
image, from the repository root, as yourself (not with `sudo`: it calls
`sudo docker` itself when your user cannot reach Docker):

```bash
tools/test-browser.sh                                     # every browser test, every project, once
tools/test-browser.sh --project=webkit                    # any `playwright test` arguments
tools/test-browser.sh tests/mocked/login.spec.ts -g TOTP
```

The script starts the browser server
(`mcr.microsoft.com/playwright:v<version>-noble`, the version of the installed
`@playwright/test`: they must match) on `ws://127.0.0.1:3123/` (`PW_PORT` for
another port), on the host's network so that it reaches
`https://localhost:4183`. It then runs `npx playwright test` with
`PW_TEST_CONNECT_WS_ENDPOINT` pointing at it, so every project's browser
(Chromium and WebKit) is the container's, and stops the container at the end,
also after a failure or Ctrl+C. Everything else runs on your machine as usual:
the builds, the preview servers, the test backend and the reports. Only the
browsers are in the container. The server runs with `--unsafe`, which passes
the projects' browser arguments on: the PWA projects need Chrome's
`--ignore-certificate-errors` (no service worker with the preview's
self-signed certificate otherwise). It listens on 127.0.0.1 only, for this run
only, and what a client asks for runs in the container. The first run downloads the image
(3.6 GB on disk; `docker image rm mcr.microsoft.com/playwright:v<version>-noble` frees it).

CI (`ubuntu-latest`) runs WebKit directly. On failure, CI uploads the HTML
report (with a trace of each step) and the backend log as the
`playwright-report` artifact; open it with `npx playwright show-report <folder>`.

### 7. PWA

The app is installable and opens offline. Pieces:

| File | Role |
|---|---|
| `static/favicon.svg` | Favicon, and the source of the app icons |
| `static/icons/*.png` | App icons (192, 512, maskable 512, Apple 180), generated from the favicon: run `npm run icons` after changing it, and commit the PNGs |
| `static/manifest.webmanifest` | Name, icons, colours, `display: standalone` |
| `src/service-worker/` | Service worker, registered by SvelteKit; type-checked with its own `tsconfig.json` (`npm run check`) |
| `src/lib/pwa.ts` | App side: persistent storage, clearing user data on logout/login, catalogue update messages, checks for a new version |
| `src/lib/UpdateBanner.svelte` | "A new version of the app is available" with **Reload**, on every page |

What the service worker does:

- **The file list is generated, never written by hand**: SvelteKit's build
  puts every output file in `$app/manifest` (`immutable`: compiled code and
  styles, content-hashed names; `assets`: `static/`). Adding a route or a
  component needs no change to the service worker.
- **App shell** (build output, static files, `/`): cached at install, one
  cache per version (`shell-<version>`); older versions are deleted when the
  new service worker takes over.
- **Page loads**: network first, else the cached shell (single-page app).
- **`/api/catalog`**: stale-while-revalidate, one entry per language. The page
  gets the cached copy at once; the service worker revalidates in the
  background (the ETag makes it a `304` when unchanged) and, when the
  catalogue changed, tells the open pages, which show the new one.
- **`/api/setup/status`, `/api/auth/me`, `/api/techniques/<id>/comments`**:
  network first (always the latest when online), the cached copy only
  offline, so the app opens without a network and shows the comments last
  seen.
- **Segment clips** (`/media/segment/<id>`): every clip played is kept for
  offline use (cache `media`). A segment's clip does not change: cache first, and the
  `Range` requests of `<video>` (seeking; Safari plays nothing without `206`)
  are answered from the saved file (`src/service-worker/range.ts`). A clip not
  saved yet is downloaded once, for the player and the cache at the same time,
  and plays while it downloads. Never two requests for one clip (the server
  sends one clip per user at a time): Safari first asks for 2 bytes, so the
  whole clip is downloaded and saved first, then every part is answered from
  it (in Safari a clip starts once it is saved); a seek during the download
  waits for it.
- **Whole videos** (`/media/video/<id>`, Videos page): saved on the device by
  the page itself (`$lib/offline.svelte.ts`), with a download of its own, not by
  the service worker: browsers stop a service worker after a while (Firefox:
  about 30 seconds, even with a pending `waitUntil`), which would cut a video of
  hundreds of MB passing through it. Until it is saved, the service worker
  doesn't touch its requests at all (the browser loads it as without a service
  worker); once saved, it answers them from the saved file, which keeps playing
  after the service worker is stopped. nginx allows four whole-video transfers
  per user: the editor's three video elements and the save. A video too big for
  the browser's storage is simply not saved (it stays a cloud).
- **Thumbnails** (`/media/segment/<id>/thumbnail`, `/media/video/<id>/thumbnail`):
  cache first, checked in the background (a `404`, segment removed, deletes it).
- **On the cards and thumbnails**, bottom right: a phone when every clip of
  that branch of the catalogue (a school, category, weapon, section, technique,
  or one segment) is saved on the device, a cloud when one is missing. Click
  the cloud to download them all for offline use, the phone to remove them;
  during a download a ring shows the progress (click to stop). Above 20 missing
  clips the app asks first. The clips are downloaded one at a time, through the
  service worker which saves them, as nginx sends one clip per user at a time (a
  clip refused because another one is playing is tried again). Logout stops the
  downloads. The buttons only show when a service worker controls the page (not
  in development). The service worker tells the open pages each time it saves
  or deletes a clip (`$lib/offline.svelte.ts`). Whole videos (Videos page)
  show the same badge, saved by opening them.
- **Everything else** (other API calls): network only, never cached.

**New versions.** The browser looks for a new service worker only when a page
loads, and an installed app is usually resumed, not reloaded. So the app also
checks (`registration.update()`) whenever it comes back to the foreground, and
every hour while it is open. A new service worker takes over at once
(`skipWaiting`, `clients.claim`) and deletes the old shell cache, but the open
page still runs the old code: it shows "A new version of the app is
available" with a **Reload** button. It never reloads by itself, since an
annotation may be in progress (upload drafts are saved; the Videos page asks
before leaving unsaved changes). Not shown on the first install.

User data (caches `data` and `media`) is deleted on logout and after each login. In
production, nginx also sends `Clear-Site-Data` on logout.

**Test it in the browser.** The service worker only runs in the production
build:

```bash
npm run build && npm run preview     # https://localhost:4173
```

Chrome refuses to register a service worker served with a self-signed
certificate, even after accepting the warning. Start a separate Chrome
profile that ignores certificate errors (only for this local test):

```bash
google-chrome --user-data-dir=/tmp/vn-chrome --ignore-certificate-errors https://localhost:4173
```

Then, in DevTools (F12) → **Application**:

- **Manifest**: name, icons, colours; warnings if something prevents installing.
- **Service workers**: status of `service-worker.js`. *Update on reload*
  avoids testing an old version; *Offline* simulates no network (reload: the
  app and the last catalogue still show).
- **Cache storage**: `shell-<version>` (app files) and `data` (catalogue per
  language, current user).
- **Storage**: usage, persistence, *Clear site data* to start over.

In **Network**, requests answered by the service worker show
"(ServiceWorker)" in the Size column. The install button appears at the right
of the address bar; **Lighthouse** checks installability. On iPhone/iPad,
install from Safari's *Share → Add to Home Screen*.

Writing tests:

- Find elements as a user does: `getByLabel('Username')`,
  `getByRole('button', { name: 'Log in' })`, not CSS classes.
- Wait with `await expect(…)` (it retries), never with fixed sleeps.
- One behaviour per test. Mocked tests for most cases; keep e2e flows few.
- TOTP codes in e2e tests are computed from the secret shown by the setup
  wizard (`otpauth`).

### 8. Uploads in development

Uploads need **tusd** (receives the files) and **ffmpeg** (encodes them). The
backend starts tusd itself when it is on `PATH` (or `VIDEONINJA_TUSD_BIN`), on
`127.0.0.1:1080`, and encodes in a background thread when `ffmpeg`/`ffprobe`
are installed; without them it logs a warning and uploads stay queued.
`npm run dev` forwards `/files` to tusd (`TUSD_URL` for another address).
Uploads and encoded videos go to `server/uploads/` and `server/media/`
(ignored by git); without nginx the app serves the thumbnails itself.

Install both first (see [Prerequisites](#prerequisites) and
[Installing tusd](#installing-tusd)), then start the backend as usual; a fast
x265 preset keeps encodings short while developing:

```bash
VIDEONINJA_DB=dev.db VIDEONINJA_DB_KEY_FILE=dev.key VIDEONINJA_X265_PRESET=ultrafast \
  uvicorn app.main:app --reload
# The log must show: "tusd started (pid …)" and "Encoder started".
```

In development `/files` reaches tusd without nginx's per-request check (see
[How uploads work](#how-uploads-work)); tusd's pre-create hook still checks the
session.

### The catalogue of techniques

Each school has its own organisation, kept as is (fixed, no free-form tree):

- **Categories** (`category`): Taijutsu 体術 (unarmed), Muto Dori 無刀捕 (unarmed
  against the sword), Buki 武器 (weapons).
- **Weapons** (`weapon`, only under Buki): Rokushakubo, Hanbo, Jo, Yari,
  Naginata, Bisento, Jutte, Kodachi, Biken, Ninjato, Shuriken.
- **Sections** (`section`): a school's scrolls and groups of forms, in its
  category (and weapon), e.g. Gyokko Ryu › Taijutsu › Jo Ryaku no Maki,
  Kukishin Ryu › Buki › Rokushakubo › Shoden Gata. The levels (Shoden,
  Chuden, Okuden) are sections named as each school names them.
- **Techniques** (`technique`): in a section.

IDs stay readable: section `<ryu>.<category>[.<weapon>].<name>`, technique
`<section>.<name>` (`gyokko.taijutsu.jo_ryaku.koku`). URLs use each step's name:
`/schools/gyokko/taijutsu/jo_ryaku/koku`,
`/schools/kukishinden/buki/rokushakubo/shoden/chudan_kangi`. Every step has its
page, even with a single card.

The content (about 640 techniques of seven schools, with kanji, romaji and an
English and French meaning) lives in `server/database/catalog/techniques.json`,
collected from public sources (listed per section). Gyokushin and Kumogakure
Ryu have none yet: no public source names their techniques. The meanings are
rough glosses, to be reviewed by a teacher. To change the catalogue, edit the
JSON, then regenerate the block of the latest `db_v<N>_init.sql` (a test fails if they
differ), and rebuild the database:

```bash
python3 tools/catalog-sql.py
server/.venv/bin/python tools/make-dev-db.py --force
```

Card emblems (background images): `frontend/src/lib/{schools,categories,weapons,sections}/emblems/<id>.svg`.
A section uses the emblem of its name (`jo_ryaku.svg`), else of its kind
(`shoden_omote` → `shoden.svg`, table in `$lib/sections/emblems.ts`); a unit
test checks that every category, weapon and section of the JSON has its own.
Techniques have no emblem.

### Database schema

The schema is designed in [drawdb](https://drawdb.app) and exported to
`server/database/db_v<N>.sql`. drawdb does not export `AUTOINCREMENT`: after each
export, re-add `"id" INTEGER PRIMARY KEY AUTOINCREMENT` on `video`, `segment`,
`user` and `comment`.

Versions: the app runs on one database version, `EXPECTED_VERSION` in
`server/app/core/db.py` (now 3), kept in the database itself (`config.db_version`).

| File | What |
|---|---|
| `db_v<N>.sql` + `db_v<N>_init.sql` | Version N's schema and initial data: the setup builds a new database from those of `EXPECTED_VERSION` |
| `migrations/v<a>_to_v<b>.sql` | One version to the next (`v1_to_v2.sql`) or back (`v2_to_v1.sql`), in one transaction, ending with the new `db_version` |

At startup, before any request, the API compares the database's version with
`EXPECTED_VERSION` and migrates it one version at a time, up (a newer release)
or down (going back to an older one). It first copies the database next to it,
`videoninja.db.v<old>-<UTC time>.bak` (delete those copies once the new version
runs well). It refuses to start, and changes nothing, if a step's script is
missing; a step that fails is rolled back and stops the start. The encoder
waits until the database has the expected version, and `/health` reports the
database as failing otherwise.

| Version | Since | Changes |
|---|---|---|
| 1 | v0.0.6 (efae32a) | — |
| 2 | the four containers | `heartbeat` (the encoder's liveness, for `/health`), `video.thumbs_dirty` (segment thumbnails made by the encoder) |
| 3 | indexes | Indexes on the columns looked up in the growing tables (video, segment, comment, session, upload), foreign keys included; no other change |

Transactions: the API and the encoder write to the same file from two
processes. Connections (`db.connect`) are in autocommit mode; every change of
several rows, or a check followed by a write, goes in `with db.write(con):`
(`BEGIN IMMEDIATE`: the write lock from the first read, committed at the end,
rolled back on any exception), several reads that must agree in
`with db.read(con):` (one snapshot). `with con:` raises: in autocommit mode it
would not be a transaction. Keep slow work (Argon2, ffmpeg) out of a write.

Changing the schema: never edit a released `db_v<N>` file. Add `db_v<N+1>.sql`
and `db_v<N+1>_init.sql` (the new complete schema and data), the two migration
scripts, raise `EXPECTED_VERSION`, and add the version's row above.
`tools/catalog-sql.py` writes the newest `_init.sql`; a catalogue change for
existing databases also needs a migration. `server/tests/test_migrations.py`
checks that migrating up and down gives exactly the schema a fresh database
of that version has.

Conventions: text is UTF-8 (`PRAGMA encoding = 'UTF-8'`). Dates are in columns
named `…_at` declared `DATETIME`, holding ISO 8601 text with the UTC offset in
one format, `2026-10-23T12:13:38+02:00` (`server/app/core/clock.py`); the API sends
them as they are. They are written in the user's timezone: the frontend sends
the browser's (`Time-Zone: Europe/Zurich`) on every API call and the app saves
it in `user.time_zone`, for writes without a browser request (tusd hooks).
Invitations and background jobs use the server's timezone (`TZ`). Offsets
differ, so the text does not sort chronologically: SQL compares and orders
dates through `datetime()` (which converts to UTC), never as plain text.
Positions inside a video stay whole seconds (`segment.begin_s`, `end_s`).

Authors: `video.uploaded_by` and `segment.created_by` (the user who added the
segment, at upload or later on the Videos page; editing a segment keeps it).
Both `ON DELETE SET NULL`. The annotation API sends display names (the user's
name, else the username), never user IDs.

Tags: a tag's name and its fixed values' names are translated (`tag.name`,
`tag_value.name`: translation IDs `tag.<id>.name`, `tag_value.<tag>.<id>.name`,
every language filled). A tag with rows in `tag_value` takes one of them
(shown sorted by name in the user's language), and `video_has_tags` /
`segment_has_tags` store that value's ID, never its name. A tag without takes
text, stored as typed and not translated, in its `value_format`: `NULL` = any
text, `year` = a year from 100 years ago to this year. Seeded (`db_v<N>_init.sql`):
location (outdoor, dojo), event (seminar, class, demo), year, country (the
249 ISO 3166-1 alpha-3 codes, e.g. `CHE`, named in English and French), and
source (YouTube, Onmitsukage, Kanninkan: where the video comes from).
Example:

```sql
INSERT INTO "translation" ("id", "en", "fr") VALUES
	('tag.place.name', 'Place', 'Lieu'),
	('tag_value.place.dojo.name', 'Dojo', 'Dojo'),
	('tag_value.place.outdoor.name', 'Outdoor', 'Extérieur');
INSERT INTO "tag" ("id", "name") VALUES ('place', 'tag.place.name');
INSERT INTO "tag_value" ("tag", "id", "name") VALUES
	('place', 'dojo', 'tag_value.place.dojo.name'),
	('place', 'outdoor', 'tag_value.place.outdoor.name');
```

### API errors

Every error the API (and nginx's own 429) answers with has one JSON shape:

```json
{"code": "segment.unknown_technique", "detail": "Unknown technique: x", "params": {"technique": "x"}}
```

`code` is stable and the frontend shows `error.<code>` from
`frontend/src/lib/messages.json` in the user's language, `params` filling its
placeholders. `detail` is English, for logs, curl and tests only. All codes,
with their HTTP status and English text, are in one table, `ERRORS` in
`server/app/core/errors.py`: raise `ApiError("<code>", param=value)`, never a bare
`HTTPException`. A new code needs its `error.<code>` message in every language;
`server/tests/test_errors.py` fails otherwise (and on a code missing from the
table). Request validation answers `validation.<kind>` (`VALIDATION` in the same
file), with the field's name in `params.field`. The setup's progress stream, whose
status is sent before it fails, carries the same object in `{"error": …}`.

In the frontend, `frontend/src/lib/api/client.ts` turns every failed call into an
`ApiError` (`status`, `code`, `params`) whose `message` is already the
translated text: pages show `e.message`, never the server's `detail`. A code the
frontend does not know (a newer server than an installed app) and an answer
without the JSON (an nginx page, a proxy's 502) fall back to a message from the
HTTP status; no answer at all is `network`. tus uploads go through the same
mapping (`uploadError` in `$lib/upload/upload.ts`).

### API types

The frontend's types for the API are generated from the backend's own schema, not
written by hand:

| File | Made by |
|---|---|
| `server/openapi.json` | `python -m app.api.openapi`: FastAPI's schema, every error as `ApiError` (`{code, detail, params}`) |
| `frontend/src/lib/api/schema.d.ts` | `npm run api:types` ([openapi-typescript](https://openapi-ts.dev)) from that file |

After changing an endpoint or a model, run `tools/api-types.sh` (both steps) and
commit both files with the change. A backend test fails while `openapi.json` is
out of date, and `npm run check` while `schema.d.ts` is. An update of FastAPI or
pydantic may change the schema's text: the same command.

The frontend calls the API only through `frontend/src/lib/api/`: one module per
domain (`auth.ts`, `users.ts`, `uploads.ts`…), each function typed from
`schema.d.ts` (`types.ts` names the types the app uses). Pages and components hold
no API URL; a unit test (`lib/api/boundary.test.ts`) fails if one appears.

`package.json` lets openapi-typescript use the project's TypeScript 6
(`overrides`): its release still declares TypeScript 5, and works with 6.

## Production

Four containers, one image each, published on Docker Hub
([thecyberdoc](https://hub.docker.com/u/thecyberdoc)):

| Container | Image | Does | Reads / writes |
|---|---|---|---|
| `nginx` | `thecyberdoc/videoninja-nginx` | The only entry point (plain HTTP, port 8080): the frontend, the catalogue and media files after the API's `X-Accel-Redirect`, uploads after the API's check | catalogue and media, read-only |
| `api` | `thecyberdoc/videoninja-api` | The FastAPI app: sessions, accesses, the database, catalogue snapshots, `/health` | database, catalogue; the encryption key (only this container) |
| `encoder` | `thecyberdoc/videoninja-encoder` | The encoding queue (`encode-videos.sh`, ffmpeg) and segment thumbnails | database, uploads, media |
| `tusd` | `thecyberdoc/videoninja-tusd` | Resumable uploads (the tusd binary alone) | uploads |

They run as UID 10001 (never root), with read-only root filesystems, no
capabilities and `no-new-privileges`. The API, the encoder and tusd are on an
internal network with no way out: only nginx is also on the network your
proxy reaches. ffmpeg, which reads what users upload, runs in a container
without the encryption key, the catalogue, or any network but the internal one.
Your own reverse proxy in front only handles TLS and forwards `/videoninja/`
to nginx: see [6. Reverse proxy and nginx](#6-reverse-proxy-and-nginx).

The images are built in stages (`server/Dockerfile`, one target per image):
the frontend (Node), the Python packages (a virtual environment), tusd, nginx's
brotli module and the nginx configuration (checked with `nginx -t`) are each
prepared in their own stage. The final images only copy their results onto
their runtime. No build step runs in them and they hold no build tool.

| Image | Base (pinned version) |
|---|---|
| nginx | `dhi.io/nginx:1.31.8-alpine3.24`: Docker Hardened Image |
| api | `python:3.15.2-alpine3.24`, without pip, with brotli, zopfli, tini, setpriv |
| encoder | `python:3.15.2-alpine3.24`, without pip, with ffmpeg + ffprobe built from source (below; checked at build: libx265, nnedi, zscale, tonemap), the x265, zimg and dav1d libraries, bash, tini, setpriv |
| tusd | `dhi.io/static:20261020-alpine3.24`: Docker Hardened Image, the tusd binary only |
| (build stages) | `dhi.io/node:26.12.1-alpine3.24-dev`, `dhi.io/alpine-base:3.24-alpine3.24-dev`, `dhi.io/nginx:1.31.8-alpine3.24-dev` |

[Docker Hardened Images](https://docs.docker.com/dhi/) are used wherever one
fits. The API and the encoder can't use one: the hardened Python images stop at
3.14 and have no package manager to add brotli, zopfli, tini and the libraries ffmpeg links. Building
pulls from `dhi.io`, which needs a (free) Docker account: `docker login dhi.io`
once on the build machine; CI logs in with the Docker Hub secrets. In the API and encoder, `tini` is PID 1: it reaps any
process left behind and passes `docker stop` on.

Target: Raspberry Pi 5 (arm64) or any amd64 host, with Docker Engine and the
Compose plugin, Docker data on a local SSD. The API and the encoder share the
SQLite database: both containers must run on the same host, on a local disk
(never NFS).

### 1. Directory and encryption key

```bash
sudo install -d -m 755 /opt/videoninja
cd /opt/videoninja
# The encryption key, in .env next to docker-compose.yaml: Compose reads it and
# passes it to the api container as VIDEONINJA_DB_KEY. Readable by root only.
sudo sh -c 'umask 077; echo "VIDEONINJA_DB_KEY=$(openssl rand -base64 32)" > .env'
# Catalogue snapshots, uploads (originals waiting to be encoded) and media
# (encoded videos and thumbnails): written by the containers (UID 10001).
sudo install -d -o 10001 -g 10001 -m 750 /srv/catalog /srv/uploads /srv/media
```

Size the SSD for the queue: originals wait in `/srv/uploads` until encoded.

The key encrypts the TOTP secrets in the database. It lives **outside** the
database volume, so a copy of the database alone reveals nothing.

**Back up the key separately from the database** (password manager, offline
copy). If the key is lost, no stored TOTP secret can be read and nobody can log
in.

      # The encryption key, from .env (step 1): not written in this file.

`FORWARDED_ALLOW_IPS: "*"`: the API takes the client's address from the
`X-Forwarded-For` header of any request that reaches it (login throttling,
logs). This is safe only if **nothing but nginx can reach the API** (port 8000):
no published port, and the `backend` network (or your own segmentation of it)
open to nginx, the encoder and tusd only, which never send that header. Anything
else that reaches the API could pretend to be any client. Without the setting,
every client looks like nginx and one attacker's failed logins throttle
everybody. (To restrict it by address instead, give nginx a fixed IP on the
backend network and set `FORWARDED_ALLOW_IPS` to it.)

`docker compose ps` shows the health of the API (which covers nginx, the
database, the encoder and tusd) and of the encoder. `curl
http://127.0.0.1:8080/videoninja/health` answers, for example,
`{"status":"degraded","database":"ok","encoder":"failing","tusd":"ok"}` with
`503` when the encoder has been down for 2 minutes. Before the setup, the
database and the encoder are `not_set_up` (and the answer `200`).

The key in `VIDEONINJA_DB_KEY` is visible to anyone who can run
`docker inspect` on the container (root or the `docker` group on this host).
Keep `.env` readable by root only and never commit it. The app removes the
variable from its environment once read, so the tools it runs never see it.
The other containers never get it.

A Docker secret keeps the key out of `docker inspect`. To use one instead of
`.env`, create the file and uncomment the two `secrets:` blocks above (and
remove the `VIDEONINJA_DB_KEY` line):

```bash
sudo install -d -m 700 secrets
sudo sh -c 'umask 077; openssl rand -base64 32 > secrets/videoninja_key'
# The api container runs as UID 10001 and must be able to read the key.
sudo chown 10001 secrets/videoninja_key
sudo chmod 400 secrets/videoninja_key
```

Compose mounts the secret with the host file's owner and mode (its `uid:` and
`mode:` options only apply to Swarm): without the `chown`, the app stops at
start with "Encryption key file not readable by this user (UID 10001)".

Set only one of `VIDEONINJA_DB_KEY` and `VIDEONINJA_DB_KEY_FILE`: with both,
the app refuses to start. Moving an existing installation from one to the
other: put the **same** key in the secret file (the value after
`VIDEONINJA_DB_KEY=` in `.env`), or nobody can log in.

Published tags, for a release `v1.2.3`, on each of the four images: `1.2.3`
(exact), `1.2` (receives patch releases), `1` and `latest`. Pin `1.2` for safe
updates, or `1.2.3` to stay put, and the **same** version for all four: they
are released together. Only tagged releases are published. (Releases before
the split, up to 0.0.x, are the single image `thecyberdoc/videoninja`.)

The published images serve the app under `/videoninja/`. For another path (or
the domain's root): build the nginx image yourself with the base path (its
frontend and configuration depend on it), and set the same path on the API
(`VIDEONINJA_BASE_PATH`) and tusd (`-base-path=<path>/files/`) in the compose
file:

```bash
docker build -f server/Dockerfile --target nginx --build-arg BASE_PATH=/other -t videoninja-nginx:other .
docker build -f server/Dockerfile --target nginx --build-arg BASE_PATH= -t videoninja-nginx:root .
```

### Users

**Failed logins** are throttled per client address: after 10 failed
credentials in 15 minutes (wrong password or authenticator code at login, wrong
current password in the profile, wrong setup or invitation token), that
address gets `429` on those forms until the oldest failure is 15 minutes old;
the page shows how long to wait. Other refusals (expired session, missing
access) never count. The count is in memory: restarting the container resets
it. Users sharing one address (a club's Wi-Fi) share the count; an attack from
many addresses is not stopped by it, the authenticator code still is. The
address is your proxy's `X-Forwarded-For`: if the proxy does not set it, every
client looks the same and one attacker throttles everybody.

Before that, nginx limits the **rate of requests** per address (`limit_req`):
60 a minute (bursts of 30) on the credential forms sent (POST) (login, setup, registration,
password and authenticator changes), 20 a second (bursts of 100) on the API, 50
a second (bursts of 300) on media, 10 a second (bursts of 50) on uploads. Over
it, nginx answers `429` itself (`Retry-After: 5`), and the page says to try again
in a moment. Password checks are capped too: at most
`VIDEONINJA_ARGON2_CONCURRENCY` at a time (each takes 64 MiB), so a burst of
logins cannot exhaust the API's memory; the others wait their turn, then get
"the server is busy".

**Writes from other sites** are refused (`403`): every request that changes
something (POST, PUT, PATCH, DELETE: the API, and the uploads, checked with the
app before tusd gets them) must come from a page of this origin. The browser
says so in `Sec-Fetch-Site` (only `same-origin` passes); older browsers without
it send `Origin`, which must name this host. Requests with neither are not a
browser's (scripts, the containers' own calls) and pass: the session cookie is
`SameSite=Strict` anyway. Under a subfolder, the domain's other sites share the
origin and pass too (see [Sharing the domain](#sharing-the-domain-subfolder)).

Users are added by invitation, from **User Management** in the user menu
(top right; only for roles with the `user_mgmt` access, i.e. admins):

1. Enter a username, choose a role, click **Create**. The app shows an
   invitation link (`https://<host>/register#<token>`), valid for **one week**,
   and copies it to the clipboard. Send it to the user.
2. The user opens the link and chooses a display name (optional), a password
   and an authenticator app. The link then stops working.

In the user list, the first column shows the state: a green check
(registered), nothing (invitation pending: the copy button gives the link
again) or a red cross (invitation expired). The reset button issues a new
link. For a registered user, reset also removes the password and
authenticator and logs the user out: that is how a lost password or
authenticator is recovered. Every user must use an authenticator app; there
is no way to log in without one. Admins cannot reset their own account.

Roles and what they allow (accesses):

| Role | `segment` | `comment` | `annotate` | `upload` | `video_mgmt` | `user_mgmt` |
|---|---|---|---|---|---|---|
| `user` | ✓ | ✓ | | | | |
| `editor` | ✓ | ✓ | ✓ | | | |
| `uploader` | ✓ | ✓ | ✓ | ✓ | | |
| `video_mgmt` | ✓ | ✓ | ✓ | ✓ | ✓ | |
| `admin` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

**Videos** (top menu, right of Upload; `video_mgmt` access) lists every
published video in four collapsible sections: **In progress** (some
techniques, not all), **To annotate** (none yet), **Complete**, and **No
technique** (marked as containing none). Each thumbnail shows the video's
duration and whether it is saved on this device.
A video opened here is saved on the device by the PWA, like clips (deleted
on logout): reopening it doesn't download it again. The phone at the right of
the page's title removes every video saved this way, at once (they take
hundreds of MB and are only needed while annotating); their thumbnails and the
clips stay, and the badges go back to the cloud. Clicking one opens the same annotation panel as the upload page,
with the video from the server and its saved segments and tags: **Proceed**
saves them (nothing is uploaded). Segments keep their ID; new or re-timed ones
get a new thumbnail, and the PWA drops saved clips of segments re-timed or
removed when it gets the new catalogue.

**Comments:** on a technique's page, **Add a comment** (with the `comment`
access) opens a form for the text and its language (the interface's by
default). Comments show the author, the language (flag) and the time of the
last change ("(edited)" once changed), last changed first. Each user edits and
deletes only their own comments, admins included: nobody can change someone
else's.

The invitation token is in the URL fragment (`#…`), which browsers never send

### Uploading videos

**Upload** (top menu, right of Schools) is shown to roles with the `upload`
access (uploaders and admins):

1. Choose a video file. It is opened on the device, not sent: its SHA-256 is
   computed and checked: "This video already exists" if it is the original
   of a video already uploaded, or the published file of one.
2. Play it, step frame by frame (⏮ ⏭ or ← →), and mark technique segments:
   drag across the film strip, or **Begin here (I)** / **End here (O)** at the
   current frame; drag a segment's edges to adjust it. Pointing at the film
   strip (also while dragging) shows that frame without moving the playhead;
   click to move it there. For each segment choose
   school › category › weapon (under Buki only) › scroll or form › technique
   (each choice narrows the next; a step with a single choice is filled in) and
   the performer (or add one), and optional tags.
3. Or choose **Define segments later** (the "all segments done" box is then
   off) or **This video does not contain any technique segment** (box on).
4. **Proceed** uploads the original (resumable, 50 MB at a time) with the
   segments. The video then waits in the server's queue; **My uploads** shows
   its place, the encoding progress, and Retry/Delete if it failed. It appears
   on the technique pages once encoded. The page can be left at any time.

Unfinished work is kept on the device and resumed by choosing the same file
again (until logout). A file the browser cannot play (some AVI/DV/MPEG-2, or
H.265 in Firefox) can still be sent with "Define segments later".

Encoding happens on the Pi, one video at a time, in software: a 1080p video
takes roughly as long as several times its duration with the `medium` preset
(measure on your Pi; `VIDEONINJA_X265_PRESET=fast` halves it). Interlaced
sources are deinterlaced (NNEDI3) and HDR ones tone-mapped, as by
`tools/encode-videos/encode-videos.sh`. A file already in that format (e.g.
encoded with the script before uploading) is not encoded: its video and audio
are copied into a new file (seconds, no quality lost). Only the format counts:
MP4 with faststart, one H.265 Main 8-bit `hvc1` video, SDR BT.709,
progressive, a keyframe at least every second, AAC mono or stereo (one audio
stream) or no audio. When encoding, the script puts a keyframe every second up
to 30 fps and every half second above (smoother seeking and frame stepping at
high frame rates; `-g` sets another interval).

Published videos never keep their metadata: tags (a phone's GPS location,
dates, device, title), chapters and other streams (data or GPS tracks,
timecode, subtitles) are removed, whether the video was encoded or only
copied. The picture's rotation (portrait videos) is kept. The published file
is therefore never byte for byte the original: both hashes are kept, and a
new upload of either is refused. The original is deleted once the video is
published; an upload not submitted within a week is deleted too.

`encode-videos.sh` used by hand (to encode before uploading) also removes the
metadata; `-m` keeps it (the server removes it anyway when publishing). Mono
audio stays mono; more than two channels are mixed down to stereo.

### 6. Reverse proxy and nginx

Two nginx: **your reverse proxy** (TLS, your domain, the `/videoninja/`
subfolder) and **the container's nginx** (everything else, configured by the
image). Your proxy only forwards; it needs no modules beyond the standard ones.

#### Your reverse proxy

In the `server` block that already serves `https://example.org` with TLS:

```nginx
# HSTS for the whole domain: here, not in the app (a subfolder must not decide
# for the domain). Add includeSubDomains only if every subdomain has HTTPS.
add_header Strict-Transport-Security "max-age=31536000" always;

location = /videoninja {
    return 301 /videoninja/;
}

location /videoninja/ {
    # No URI after the address: /videoninja/… is forwarded unchanged (the
    # container serves under /videoninja/).
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Connection        "";
    proxy_set_header Host              $host;
    # The container builds upload URLs from these (https, your domain and port).
    proxy_set_header X-Forwarded-Host  $http_host;
    proxy_set_header X-Forwarded-Proto $scheme;
    # Overwrite, never append ($proxy_add_x_forwarded_for): the container
    # trusts this single value as the client's address.
    proxy_set_header X-Forwarded-For   $remote_addr;

    # Uploads: 50 MB chunks, streamed to the container (no temporary copy),
    # with time for a slow link.
    client_max_body_size    64m;
    proxy_request_buffering off;
    proxy_read_timeout      300s;
    proxy_send_timeout      300s;
    # Pass answers on as they come: the setup wizard's progress, video.
    proxy_buffering off;
}
```

Check, then reload: `sudo nginx -t && sudo nginx -s reload`. The other sites
of the domain are not affected; the `add_header` line applies to the whole
`server` block (if a `location` there has its own `add_header`, repeat it
there: nginx does not merge them).

Then check from outside:

```bash
curl -sI https://example.org/videoninja/ | grep -iE '^(HTTP|content-type|strict-transport)'
# HTTP/2 200, content-type: text/html; charset=utf-8, strict-transport-security: …
curl -s https://example.org/videoninja/health      # {"status":"ok"}
```

#### Sharing the domain (subfolder)

Under a subfolder, Video Ninja has the same **origin** (`https://example.org`)
as everything else on the domain, and browsers isolate by origin, not by
path. Accepted for this setup, with these consequences and mitigations:

- Pages of the domain's other sites can read Video Ninja's browser storage
  (cached catalogue, clips, upload drafts) and call its API with the user's
  cookie: an XSS in any of them reaches Video Ninja. CSP `'self'` covers the
  whole origin too.
- The session cookie is limited to the app: `__Secure-session` with
  `Path=/videoninja` (at the domain's root it is `__Host-session`, `Path=/`).
  The other sites' servers never receive it.
- Logout sends `Clear-Site-Data: "cache", "storage"`, which clears the
  browser's cache and storage **for the whole origin**, so also for the
  domain's other sites (logged-in state kept in their local storage, their
  offline data).
- HSTS comes from your proxy, for the domain.

A subdomain (`videoninja.example.org`) isolates the app completely: build the
image with `BASE_PATH=` (empty) and proxy the whole subdomain to it.

#### The nginx container

[`nginx/nginx.conf`](nginx/nginx.conf), in the `videoninja-nginx` image, runs
as UID 10001, writes only to `/tmp`, and logs to the container's output
(`docker compose logs nginx`). It:

- serves the frontend (the SvelteKit build in `/srv/www/videoninja/`) with its
  precompressed `.br`/`.gz` files and the caching headers (hashed files
  forever, the rest revalidated);
- removes the base path and proxies `/videoninja/api/` and `/videoninja/media/`
  to the API (`api:8000` on the internal network);
- serves catalogue and media after the app's `X-Accel-Redirect` (below);
- checks every upload request with the app (`auth_request`) before tusd
  (`tusd:1080`) gets it;
- sends the security headers (CSP, `Referrer-Policy: no-referrer`, …) and
  takes the client's address from `X-Forwarded-For`, trusted only from
  private addresses (your proxy);
- limits the rate of requests per address (`limit_req`, see [Users](#users)),
  answering `429` itself, as JSON with `Retry-After`;
- sends **one clip per user at a time** (whole videos on the Videos page: four
  transfers per user, its own count: the editor's three video elements and the
  download that saves the video on the device). The app puts the user's ID in the
  internal redirect (`/protected-clip/<user id>/…`, `/protected-video/<user id>/…`)
  and nginx counts the transfers in progress (`limit_conn`): a second one gets
  `429`, and the player says that another video is still downloading (a clip
  being saved for offline use counts too). A transfer ends when the file is
  sent or the browser goes away. Thumbnails are not limited. Without nginx
  (development) there is no limit.

The API and tusd are on the internal network only: nginx is the only way in.
It finds them through Docker's DNS at each request (`resolver 127.0.0.11`): a
container recreated with a new address is reached again without restarting
nginx. nginx never forwards `/internal/` (the tusd hooks and the encoder's
catalogue call). The image is the hardened nginx (`dhi.io/nginx`, pinned
version), built with the `mp4`, `auth_request`, `gzip_static` and `realip`
modules. `brotli_static` is not among them: the build compiles it in the
image's `-dev` variant (Google's `ngx_brotli`, a pinned commit, checksums
checked) against that very nginx, and the image gets only the module. Updating
the nginx image means updating `NGINX_SOURCE` and `NGINX_SHA256` in
`server/Dockerfile` (the build stops otherwise). The image's entrypoint is not
used: the command starts nginx with this configuration.
The image runs `nginx -t` on the configuration when it is built. The
configuration is written for `/videoninja/`; the `BASE_PATH` build argument
rewrites it (and builds the frontend) for another path.

Every `add_header` is set once, in the `server` block, with per-path values
from `map`s: nginx drops all inherited `add_header`s in a location that has
its own, so no location has any.

#### Compression: precompressed only

nginx never compresses at request time (`gzip off`). Every compressible file is
compressed once, when it is written, and nginx picks the variant that matches
the browser's `Accept-Encoding` (`brotli_static` / `gzip_static`, with
`Vary: Accept-Encoding`):

| File | Written by | Variants |
|---|---|---|
| `catalog.<lang>.<hash>.json`, `annotations/<id>.<hash>.json` | the app, on each snapshot | `.br` (`brotli -q 11`), `.gz` (Zopfli) |
| `/_app/immutable/*`, `index.html`, `service-worker.js` | `npm run build` (`precompress: true` in adapter-static) | `.br`, `.gz` |
| Videos, thumbnails, filmstrips | — | none: already compressed |

Brotli at maximum level is slow but runs only when the catalogue changes, and
is typically 15–25 % smaller than gzip on JSON. Zopfli writes standard gzip
files about 5 % smaller than `gzip -9`, as the fallback. Zstandard and
Compression Dictionary Transport are not used: no reliable Safari support, and
ETag + `304` already makes updates cheap.

Check, through nginx with a valid session cookie:

```bash
curl -sI -H 'Accept-Encoding: br' -b '__Secure-session=…' https://example.org/videoninja/api/catalog \
  | grep -iE 'content-encoding|vary|etag'
# Content-Encoding: br, Vary: Accept-Encoding, ETag: "…"
```

#### Catalogue updates

- The app writes the snapshot in `/srv/catalog`:
  `versions/<version>/catalog.<lang>.<hash>.json` with its `.br` and `.gz`,
  and a `manifest.json`; `current` is a symlink to the latest version,
  swapped atomically. A version is never changed once written.
- It is rebuilt at startup, after setup, and after every write that changes
  the catalogue, whoever makes it (admins, editors, uploaders…), debounced
  (2 s): a burst of edits makes one rebuild. An unchanged catalogue makes no
  new version, so the ETag stays the same and clients keep getting `304`.
  The 3 previous versions are kept for requests in flight, older ones deleted.
- `/api/catalog` (session check, then `X-Accel-Redirect` to
  `/protected-catalog/<version>/catalog.<lang>.<hash>.json`) has a stable URL
  and is served `private, no-cache` with an ETag. It must not be `no-store`:
  the browser keeps it and revalidates with `If-None-Match`.
- The service worker uses stale-while-revalidate: it shows the cached
  catalogue at once and revalidates in the background, usually getting a
  `304` of a few bytes.
- A few thousand segments is a few hundred KB of JSON, typically under 100 KB
  compressed. Past roughly 1–2 MB compressed, split it by school
  (`catalog.<ryu>.<lang>.<hash>.json` plus a small index file), still as
  pre-generated static files.

#### How media access works

Media and catalogue files are served with **`X-Accel-Redirect`**:

1. The browser requests `/videoninja/media/segment/42` (with its session
   cookie; browsers send cookies on `<video>` requests). Thumbnails:
   `/videoninja/media/segment/42/thumbnail`.
2. nginx proxies it to the app (as `/media/segment/42`). The app checks the session, looks up the
   segment and computes start/end itself.
3. The app answers with an empty body and
   `X-Accel-Redirect: /protected/ab/<sha256>/video.mp4?start=12&end=27`, or
   `401`/`403`/`404`.
4. nginx serves the file from an `internal` location. With `start`/`end`, the
   `mp4` module returns a valid standalone MP4 for just that range: it rebuilds
   the index (`moov` atom) and streams the relevant bytes, with no transcoding.
   The index comes first, so the clip plays while the rest downloads; it
   starts on the keyframe at or before `start` (one every second).

Without nginx (development), the app cuts each clip once itself, with
`ffmpeg -c copy` (same keyframe rule), into `server/media/clips/`, and serves
it with `Range` support.

The `Range` header survives the internal redirect, so every seek is a
`206 Partial Content` from nginx, and every seek goes through the app check
again. The mp4 output is deterministic (same file, same start/end, same
bytes), so successive range requests fit together.

Alternatives considered:
- `auth_request`: also one app call per request, but the app cannot choose
  the file or the range; the client would have to send them.
- `secure_link`: nginx checks an HMAC itself, with no app call per seek, which
  is the lightest option for a Pi. If used, the signed string must include the
  range (`$secure_link_expires$uri$arg_start$arg_end secret`) so nobody can
  widen it. **Not used for now:** a signed link stays valid after logout,
  session expiry or account removal until it expires, which breaks the rule
  that the app decides on every request. The per-seek cost of
  `X-Accel-Redirect` is one SQLite lookup, small at this scale.

#### How uploads work

Large files go to **tusd** (its own container) with the tus protocol: the
browser creates the
upload, then sends it in 50 MB chunks (`PATCH`), each a bounded, retryable
request; after an interruption it asks for the offset (`HEAD`) and continues.

- **Every** request to `/videoninja/files/` is first checked by the app with
  `auth_request` (session, `upload` access, and the upload is the user's own),
  so the app decides on each chunk, as for media. tusd's `pre-create` hook
  checks again (also the size and the file's extension: an unknown type gets
  `415`) and names the upload; `post-finish` marks it complete. The upload page
  refuses a file too large or of another type before reading it
  (`GET /api/uploads/limits`).
- nginx streams the chunks to tusd (`proxy_request_buffering off`): no
  temporary copy on the Pi. `client_max_body_size 64m` is one chunk;
  the file size is limited by tusd (`-max-size`) and the app
  (`VIDEONINJA_MAX_UPLOAD_BYTES`, 20 GiB).
- tusd runs with `-disable-download`: uploads cannot be read back.
- The encoder container takes the oldest queued video, checks the original
  (complete, SHA-256 as announced), encodes it with `encode-videos.sh` at low
  priority, writes `video/<h2>/<sha256>/{video.mp4, thumb.jpg,
  segment-<id>.jpg}`, publishes it and asks the API to rebuild the catalogue.
  A restart puts an interrupted encoding back in the queue (3 tries at most; a
  clean stop does not count as a try).
- ffmpeg and ffprobe read local files only (`-protocol_whitelist file`: no
  network, no playlists pointing elsewhere), in the allowed formats only
  (`-format_whitelist`, `VIDEONINJA_INPUT_FORMATS`), judged by the content,
  not the name. Each ffmpeg run stops after `VIDEONINJA_FFMPEG_TIMEOUT_H` (24 h
  by default: the Pi is slow), each ffprobe run after
  `VIDEONINJA_FFPROBE_TIMEOUT_MIN` (10 min); the video then fails for good. Each runs in its own
  process group, stopped as a whole, and dies with the encoder if the encoder
  dies; `tini` reaps whatever is left: no orphan keeps encoding, no zombie.
- Segments added or moved on the Videos page get their thumbnail from the
  encoder too, within seconds (the API has no ffmpeg and cannot write the
  media); meanwhile they show their video's thumbnail.

#### Frontend side of the contract

- **Range requests from the cache:** a clip played from the Cache API needs
  proper `206 Partial Content` answers, or seeking and even playback break
  (Safari in particular). The service worker answers them from the saved clip
  (`src/service-worker/range.ts`). Clips are saved **without** a `Range`
  header, so that the full `200` response is stored.
- **Cookie:** `__Secure-session` with `Path=/videoninja` under a subfolder
  (`__Host-session`, `Path=/` at the domain's root), `HttpOnly; Secure;
  SameSite=Strict`. Works with `<video>`, since browsers send cookies on
  same-origin media requests.
- **Audit trail:** nginx logs the final status of every request (`401`/`403` =
  denied); the app logs each allow/deny decision with user and segment ID.

### 7. Logs

Each container logs to journald (the compose file's `logging`), tagged
`docker-videoninja-<container>`. The API and the encoder write one JSON object
per line (`VIDEONINJA_LOG_FORMAT=json` in the images); nginx writes its access
log as text.

| Field | What |
|---|---|
| `ts`, `level`, `logger`, `msg` | Time (with its UTC offset), level, where (`app.encoder.queue`, `app.audit`, `uvicorn.error`…), the message |
| `request_id` | The request's ID: nginx's `$request_id`, also `rid=` in nginx's log and `X-Request-ID` in the answer the browser got |
| `user_id` | Who, once the session is checked (IDs, never usernames) |
| `video_id` | The encoder's lines of a video (encoding, thumbnails) |
| `method`, `route`, `status`, `duration_ms` | `app.middleware`'s line per request; `route` is the template (`/api/videos/{video_id}/annotations`), never the path's IDs or tokens |
| `event` | `app.audit`'s security events (below) |
| `exc` | The traceback of an error |

```sh
# Follow the API, readable
journalctl -t docker-videoninja-api -f -o cat | jq -c '{ts, level, logger, msg}'
# Everything about one request (the ID from nginx's log, or from the browser's X-Request-ID)
journalctl -t docker-videoninja-api -o cat | jq -c 'select(.request_id == "3f2a…")'
# Errors and warnings of the last day
journalctl -t docker-videoninja-api -t docker-videoninja-encoder --since -1d -o cat | jq -c 'select(.level != "INFO")'
# A video's encoding
journalctl -t docker-videoninja-encoder -o cat | jq -c 'select(.video_id == 42)'
```

**Security events** (`logger` `app.audit`, `event` one of a fixed list, in
`server/app/domain/audit.py`): `setup.completed`; `login.succeeded`, `login.failed`
(with the client's address, never the username typed), `logout`,
`credentials.throttled`; `password.wrong`, `password.changed`, `totp.replaced`,
`totp.undecryptable`; `user.invited`, `user.reset`, `user.registered`,
`invite.shown`; `access.denied`, `request.cross_site`, `comment.denied`,
`upload.denied`; `upload.accepted`, `video.submitted`, `video.retried`,
`video.deleted`, `annotations.saved`, `comment.created`, `comment.edited`,
`comment.deleted`. Refusals and failures are warnings, the rest info. They carry
who (`user_id`) and what (`target_user_id`, `video_id`, `comment_id`…), never a
password, token or TOTP secret.

```sh
# Failed logins and refusals of the last week
journalctl -t docker-videoninja-api --since -7d -o cat \
  | jq -c 'select(.logger == "app.audit" and .level != "INFO") | {ts, event, client, user_id}'
```

`/health` checks the database's integrity (`PRAGMA quick_check`, which reads
the whole file) at its first call and then hourly, not on every healthcheck.

## Security

### SBOM (SPDX)

What the app is made of, package by package (OS packages, Python, npm, binaries),
in [SPDX](https://spdx.dev) JSON:

- **Published images:** each release carries its SBOM and its build provenance
  (SLSA), attached by CI (BuildKit, `sbom: true`):
  `docker buildx imagetools inspect thecyberdoc/videoninja-api:1.2.3 --format '{{ json .SBOM }}'`.
- **Every week** (and on demand: Actions → Security → Run workflow): the
  `Security` workflow builds the four images, writes their SBOMs and the
  sources' (`videoninja-*.spdx.json`, as artifacts of the run) and scans them.
- **Locally:** `tools/sbom.sh` (the images of `tools/docker-dev.sh build`) writes
  `sbom/videoninja-{nginx,api,encoder,tusd,sources}.spdx.json`; `--scan` adds a
  vulnerability table per SBOM (`sbom/*.vulns.txt`). Syft and Grype run from their
  official images, pinned by digest.

### Python dependencies: locked, with hashes

`server/requirements.in` (the app's own dependencies) and
`server/requirements-dev.in` (plus the development tools) are the files to edit.
`requirements.txt` and `requirements-dev.txt` are generated from them: every
package the app ends up with, pinned, with the hashes of all its files (every
platform: amd64, arm64, glibc, musl). pip refuses a file whose hash differs
(`--require-hashes`): a package replaced on PyPI, or a mirror serving something
else, stops the install. After editing an `.in` file, in `server/`:

```bash
uv pip compile requirements.in --universal --python-version 3.15 --generate-hashes -o requirements.txt
uv pip compile requirements-dev.in --universal --python-version 3.15 --generate-hashes -o requirements-dev.txt
pip install --require-hashes -r requirements-dev.txt
```

To update every dependency within the pins (dependencies of dependencies), add
`--upgrade` to both compile commands. Commit the `.in` and `.txt` files together.

### Code scanning

| Tool | What | Where |
|---|---|---|
| [CodeQL](https://codeql.github.com) | The Python backend, the frontend's JavaScript/TypeScript (not the `.svelte` templates) and the workflows (`actions`: injections, permissions) | GitHub's **default setup** (Settings → Code security → CodeQL analysis): every push, pull request and week, maintained by GitHub; results in **Security → Code scanning**. More queries: set its query suite to *Extended*. (A CodeQL workflow in the repository as well is refused by GitHub while the default setup is on.) |
| [Bandit](https://bandit.readthedocs.io) | Python security linter (shell calls, SQL built from strings, URLs that can open files…) | CI's server tests (a finding fails them); locally `bandit -r app -q` |

A Bandit finding that is reviewed and harmless is marked on its line, the
reason first: `import subprocess  # only through procs.py  # nosec B404`. Never
mark a whole file or test as ignored. Today's marks: `subprocess` (argument lists
built by the app, no shell), SQL statements whose table or column names are the
module's own constants, and the two internal URLs (`VIDEONINJA_API_URL`, `VIDEONINJA_TUSD_URL`), which
the app now only accepts as `http(s)` (a `file:` URL would read local files).

### Known vulnerabilities

[Grype](https://github.com/anchore/grype) matches the SBOMs against the
vulnerability databases (NVD, GitHub advisories, Alpine and Debian trackers). The
weekly workflow puts the results in the repository's **Security → Code
scanning** tab, per image and for the sources: a new vulnerability in an
unchanged image shows up there without any push. It never fails the build; read
each finding (does the vulnerable function run here? is a fixed version out?)
and update. Enable **Dependabot alerts** in the repository's settings too.

### Versions: pinned, and how updates come

| What | Pinned by | Updated by |
|---|---|---|
| Python packages | `server/requirements.txt`: every package, dependencies of dependencies too, with the SHA-256 of each file (`pip install --require-hashes`, in the image and CI) | Dependabot (pip), or by hand (below) |
| npm packages | `package-lock.json` (versions and sha512 hashes, `npm ci`) | Dependabot (npm) |
| Base images | exact tag in `server/Dockerfile` | Dependabot (docker; `dhi.io` with the Docker Hub secrets as Dependabot secrets) |
| tusd | its source (version + SHA-256), built with the latest Go (`dhi.io/golang`, Dependabot) and its Go libraries raised to their fixed versions (`TUSD_MODULES` in `server/Dockerfile`, checked against `go.sum` and sum.golang.org) | by hand: a new tusd release, or a Go library the weekly scan flags |
| nginx source, ngx_brotli | version + SHA-256 in `server/Dockerfile` | by hand (watch their releases) |
| ffmpeg | its source (`FFMPEG_VERSION` + `FFMPEG_SHA256` in `server/Dockerfile`, of the tarball signed by FFmpeg's release key), built against the runtime's Alpine: only FFmpeg's own codecs and filters, libx265, zimg, dav1d; no network protocols, no libavdevice (Alpine 3.24 ships 8.1, without the fixes of 9.0) | by hand: a new FFmpeg release (the weekly Security workflow opens an issue; check the tarball's signature), or a CVE the weekly scan flags |
| Alpine / Debian packages (`apk add`) | not pinned: the base image's current ones | a rebuild (the weekly scan says when) |
| GitHub Actions | tags (`ci-cd.yml`), commits (`security.yml`) | Dependabot (github-actions) |

Dependabot (`.github/dependabot.yml`) opens a pull request per update, weekly,
for a release at least **14 days old** (`cooldown`), time for a broken or
malicious release to be noticed and withdrawn; CI tests each pull request.
Security updates skip the wait (Dependabot opens them at once): a version pinned
by hand (an `.in` file, `TUSD_MODULES`) follows the same rule, never older than
the release that fixes a known vulnerability.
Before merging: read the release notes (breaking changes, security fixes), let
CI run, and run `tools/test-e2e-stack.sh` for anything in the images.
