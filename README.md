# Video Ninja

Installable web app (PWA) for Ninjutsu technique videos, organised by
school (ryu) → level → technique → video segments, with annotations.
Self-hosted on a Raspberry Pi 5 with Docker behind nginx.

#### Installing tusd

tusd is a single binary, installed for your user only (no sudo). The backend
finds it on `PATH`, or at `VIDEONINJA_TUSD_BIN`. The checksum is the one
published with the release (also pinned in `server/Dockerfile`):

```bash
# amd64 (most PCs). On arm64 (Raspberry Pi, Apple silicon Linux VMs) use the
# second ARCH/SHA line instead.
ARCH=amd64 SHA=e8c8d7738275d2d9377db953aecbc242262d3620e77fbd3c1491361d9cea6ac8
# ARCH=arm64 SHA=134e575a6524698b54d989958c680f0a4ec243d9622c1926e30e27c2a86e4752

cd "$(mktemp -d)"
curl -sSLO "https://github.com/tus/tusd/releases/download/v2.10.1/tusd_linux_$ARCH.tar.gz"
echo "$SHA  tusd_linux_$ARCH.tar.gz" | sha256sum -c     # must print: OK
tar -xzf "tusd_linux_$ARCH.tar.gz"
mkdir -p ~/.local/bin && mv "tusd_linux_$ARCH/tusd" ~/.local/bin/
tusd -version                                        # Version: v2.10.1
```

If `tusd -version` is not found, add `~/.local/bin` to `PATH` (e.g.
`export PATH="$HOME/.local/bin:$PATH"` in `~/.bashrc`), then open a new
terminal.

### 1. Get the code

```bash
git clone git@github.com:the-cyber-doc/VideoNinja.git
cd VideoNinja
```

Everything happens on `main`, for development and releases. Commit to `main`
directly, or use a short-lived feature branch and a pull request to `main`.

Every push, on any branch, runs CI: backend tests, frontend type-check and
build, and the Docker image build for amd64 and arm64. Nothing is published.
Keep `main` green. Users only get what is released with a tag (see
[Releasing](#releasing)).

### 2. Backend (terminal 1)

```bash
cd server
# uv downloads Python 3.15 if needed; --seed puts pip in the venv.
# (With a system Python 3.15: python3.15 -m venv .venv)
uv venv --python 3.15 --seed .venv
. .venv/bin/activate
pip install -r requirements-dev.txt

# Encryption key for development (32 random bytes, base64). Never commit it.
python -c "import base64, os; print(base64.b64encode(os.urandom(32)).decode())" > dev.key

VIDEONINJA_DB=dev.db VIDEONINJA_DB_KEY_FILE=dev.key uvicorn app.main:app --reload
```

The API listens on `http://localhost:8000`. `dev.db`, `dev.key` and the
catalogue snapshots in `catalog/` are ignored by git.

| Variable | Default | Purpose |
|---|---|---|
| `VIDEONINJA_DB` | `/data/videoninja.db` | SQLite database file. If missing, the app starts in setup mode. |
| `VIDEONINJA_DB_KEY_FILE` | `/run/secrets/videoninja_key` | Key that encrypts the TOTP secrets in the database. The app does not start without it. |
| `VIDEONINJA_DB_KEY` | unset | The key itself (base64), instead of a file. Setting it together with `VIDEONINJA_DB_KEY_FILE` refuses the start. The app removes it from its environment once read, so nginx, tusd and ffmpeg don't inherit it. Prefer the file (Docker secret): a variable shows in `docker inspect`. |
| `VIDEONINJA_CATALOG_DIR` | `catalog/` next to the database (image: `/srv/catalog`) | Catalogue snapshots (static JSON files, see [Catalogue updates](#catalogue-updates)). |
| `VIDEONINJA_X_ACCEL` | unset (image: `1`) | `1`: behind nginx, `/api/catalog` answers with `X-Accel-Redirect` and nginx sends the file. Unset: the app sends the file itself (development, no nginx). |
| `VIDEONINJA_MEDIA_DIR` | `media/` next to the database (image: `/srv/media`) | Encoded videos and thumbnails (`video/<h2>/<sha256>/…`), written by the encoding queue. Without nginx the app serves the thumbnails from here. |
| `VIDEONINJA_UPLOAD_DIR` | `uploads/` next to the database (image: `/srv/uploads`) | tusd's folder: originals waiting to be encoded. |
| `VIDEONINJA_MAX_UPLOAD_GB` | `20` | Largest upload accepted (tusd and the app). |
| `VIDEONINJA_X265_PRESET` | `medium` | libx265 preset of the encoding queue (`ultrafast` … `veryslow`; slower = smaller files). Case, spaces and quotes are ignored; any other value stops the app at start, naming the value received. |
| `TZ` | system timezone (image: UTC) | Server's timezone (IANA name, e.g. `Europe/Zurich`), for dates written without a user: invitations. Users' dates are in their browser's timezone. |
| `VIDEONINJA_BASE_PATH` | `''` (image: `/videoninja`) | Where the browser sees the app (a subfolder of the domain). The session cookie's name and path and tusd's upload URLs follow it; the frontend is built with the same value (`BASE_PATH`). |
| `VIDEONINJA_NGINX_CONF` | unset (image: `/app/nginx/nginx.conf`) | The app starts nginx with this configuration (and restarts it). Unset: no nginx (development: Vite serves the frontend). `VIDEONINJA_NGINX=0`: never; `VIDEONINJA_NGINX_BIN`: another binary. |
| `VIDEONINJA_TUSD` / `VIDEONINJA_ENCODER` | on | `0`: don't start tusd / the encoding thread (tests). tusd also needs the binary (`PATH` or `VIDEONINJA_TUSD_BIN`), encoding needs `ffmpeg`. |

### 3. Frontend (terminal 2)

SvelteKit needs Node.js ≥ 22.17; distribution packages are often older
(`npm ci` then fails with `EBADENGINE`). Install Node.js 24 LTS in your home
directory with [fnm](https://github.com/Schniz/fnm), no sudo needed:

```bash
curl -fsSL https://fnm.vercel.app/install | bash
exec $SHELL                 # reload the shell so fnm is on PATH
fnm install 24
fnm default 24
node --version              # v24.x
```

[nvm](https://github.com/nvm-sh/nvm) works too (`nvm install 24 && nvm alias default 24`).
A system Node.js can stay installed: fnm's comes first on `PATH`.

```bash
cd frontend
npm ci
npm run dev
```

Open **https://localhost:5173** and accept the self-signed certificate once.
The dev server runs over HTTPS because the session cookie is `Secure`, as in
production. It forwards `/api` to the backend on port 8000.

### 4. First start

With no database, the backend prints a one-time setup token in terminal 1:

```
WARNING:  Video Ninja is not set up yet. Setup token: 3q2-…
```

The app opens the setup wizard: enter the token, create the admin account
(password + authenticator app), and the database is built. Then log in.

To start over, stop the backend and delete `server/dev.db` (and
`dev.db-wal` / `dev.db-shm` if present) and `server/catalog/`.

#### Test admin without the wizard

`tools/make-dev-db.py` builds the database outside the app, like the wizard
does (the latest `db_vN.sql` + `db_vN_init.sql`), with an admin whose
credentials are fixed in the script: add its TOTP secret to your
authenticator once, and every rebuilt database logs in the same way.

```bash
# From the repository root, the backend stopped. Key: server/dev.key (required).
server/.venv/bin/python tools/make-dev-db.py            # creates server/dev.db
server/.venv/bin/python tools/make-dev-db.py --force    # replaces it (and its -wal/-shm)
```

| Variable in the script | Value |
|---|---|
| `USERNAME` | `admin` |
| `PASSWORD` | `XhvqKL3zKA7S` |
| `TOTP_SECRET` | `J3BFCBSLVAZSG3M7POCBI235XUL35XUQ` (base32; `oathtool --totp -b <secret>` prints the current code) |

Change them in the script; it checks them against `server/app/validation.json`.
These credentials are public: use such a database for development and test
instances only, never in production. The catalogue snapshot is rebuilt at the
backend's next start. `--db` and `--key` choose other files.

For a test instance on the Raspberry Pi (fresh install, before its first
start), build the database on your machine with the Pi's key, then copy it
into the container's `data` volume, owned by the container's user:

```bash
# On your machine: the Pi's key (from /opt/videoninja/.env) in a temporary file
umask 077; echo '<the base64 key>' > pi.key
server/.venv/bin/python tools/make-dev-db.py --db videoninja.db --key pi.key
rm pi.key
# On the Pi, in /opt/videoninja, with videoninja.db copied there:
sudo chown 10001:10001 videoninja.db
sudo docker compose create
sudo docker compose cp -a videoninja.db server:/data/videoninja.db
sudo docker compose up -d && sudo rm videoninja.db
```

### 6. Frontend tests

Two levels, both run by CI on every push:

| Command | Tool | What | Speed |
|---|---|---|---|
| `npm run test:unit` | [Vitest](https://vitest.dev) | Plain functions, files `src/**/*.test.ts` next to the code | milliseconds |
| `npm run test:browser` | [Playwright](https://playwright.dev) | Pages in real browsers, files in `tests/` | seconds |

`npm test` runs both.

Browser tests come in two kinds:

- **`tests/mocked/`**: the API is faked with `page.route`, no backend needed.
  For page behaviour and error cases that are hard to produce for real. Run
  in Chromium and WebKit (Safari's engine).
- **`tests/pwa/`**: the service worker on the production build: manifest and
  icons, offline start with the cached catalogue, catalogue update, caches
  cleared on logout. The API is faked with `context.route` (`page.route` does
  not see the service worker's requests; the mocked tests block the service
  worker for that reason). Chromium only.
- **`tests/e2e/`**: full flows against the real backend (setup → login →
  logout → profile: name, password, authenticator). Playwright starts a fresh backend on port 8001
  (`tests/e2e/backend.sh`: new database and key in `frontend/.e2e/`, setup
  token read from `.e2e/server.log`), so a dev backend on 8000 is not
  affected. Chromium only; the tests run in order.

Playwright also builds the app (every run) and serves it with `vite preview`
on `https://localhost:4183`, not 4173, so a preview you started yourself is
never mistaken for the test build. The e2e backend needs the backend's virtual
environment (`server/.venv`, see [Backend](#2-backend-terminal-1)), or another
Python with the dependencies in `PYTHON`.

First run, in `frontend/`:

```bash
npx playwright install chromium webkit   # browsers, in ~/.cache/ms-playwright
npm run test:browser
```

Useful options:

```bash
npx playwright test --project chromium --project pwa --project e2e   # skip WebKit
npx playwright test --ui              # interactive: step through, see each action
npx playwright test --headed          # watch the browser
npx playwright codegen https://localhost:4173   # record clicks as test code (your own preview)
```

WebKit needs system libraries (`sudo npx playwright install-deps webkit`).
Playwright officially supports Ubuntu 22.04 and 24.04 LTS; on other
distributions WebKit may not start, so run Chromium locally and let CI
(`ubuntu-latest`) run WebKit. On failure, CI uploads the HTML report (with a
trace of each step) and the backend log as the `playwright-report` artifact;
open it with `npx playwright show-report <folder>`.

### 7. PWA

The app is installable and opens offline. Pieces:

| File | Role |
|---|---|
| `static/favicon.svg` | Favicon, and the source of the app icons |
| `static/icons/*.png` | App icons (192, 512, maskable 512, Apple 180), generated from the favicon: run `npm run icons` after changing it, and commit the PNGs |
| `static/manifest.webmanifest` | Name, icons, colours, `display: standalone` |
| `src/service-worker/` | Service worker, registered by SvelteKit; type-checked with its own `tsconfig.json` (`npm run check`) |
| `src/lib/pwa.ts` | App side: persistent storage, clearing user data on logout/login, catalogue update messages, checks for a new version |
| `src/lib/UpdateBanner.svelte` | "A new version of the app is available" with **Reload**, on every page |

What the service worker does:

- **The file list is generated, never written by hand**: SvelteKit's build
  puts every output file in `$app/manifest` (`immutable`: compiled code and
  styles, content-hashed names; `assets`: `static/`). Adding a route or a
  component needs no change to the service worker.
- **App shell** (build output, static files, `/`): cached at install, one
  cache per version (`shell-<version>`); older versions are deleted when the
  new service worker takes over.
- **Page loads**: network first, else the cached shell (single-page app).
- **`/api/catalog`**: stale-while-revalidate, one entry per language. The page
  gets the cached copy at once; the service worker revalidates in the
  background (the ETag makes it a `304` when unchanged) and, when the
  catalogue changed, tells the open pages, which show the new one.
- **`/api/setup/status`, `/api/auth/me`, `/api/techniques/<id>/comments`**:
  network first (always the latest when online), the cached copy only
  offline, so the app opens without a network and shows the comments last
  seen.
- **Segment clips** (`/media/segment/<id>`): every clip played is kept for
  offline use (cache `media`). A segment's clip does not change: cache first, and the
  `Range` requests of `<video>` (seeking; Safari plays nothing without `206`)
  are answered from the saved file (`src/service-worker/range.ts`). A clip not
  saved yet is downloaded once, for the player and the cache at the same time,
  and plays while it downloads. Never two requests for one clip (the server
  sends one clip per user at a time): Safari first asks for 2 bytes, so the
  whole clip is downloaded and saved first, then every part is answered from
  it (in Safari a clip starts once it is saved); a seek during the download
  waits for it.
- **Whole videos** (`/media/video/<id>`, Videos page): saved on the device by
  the page itself (`$lib/offline.svelte.ts`), with a download of its own, not by
  the service worker: browsers stop a service worker after a while (Firefox:
  about 30 seconds, even with a pending `waitUntil`), which would cut a video of
  hundreds of MB passing through it. Until it is saved, the service worker
  doesn't touch its requests at all (the browser loads it as without a service
  worker); once saved, it answers them from the saved file, which keeps playing
  after the service worker is stopped. nginx allows four whole-video transfers
  per user: the editor's three video elements and the save. A video too big for
  the browser's storage is simply not saved (it stays a cloud).
- **Thumbnails** (`/media/segment/<id>/thumbnail`, `/media/video/<id>/thumbnail`):
  cache first, checked in the background (a `404`, segment removed, deletes it).
- **On the thumbnails**, bottom right: a phone when the clip or video is saved
  on the device (it plays offline), a cloud when it isn't. The service worker
  tells the open pages each time it saves or deletes one
  (`$lib/offline.svelte.ts`).
- **Everything else** (other API calls): network only, never cached.

**New versions.** The browser looks for a new service worker only when a page
loads, and an installed app is usually resumed, not reloaded. So the app also
checks (`registration.update()`) whenever it comes back to the foreground, and
every hour while it is open. A new service worker takes over at once
(`skipWaiting`, `clients.claim`) and deletes the old shell cache, but the open
page still runs the old code: it shows "A new version of the app is
available" with a **Reload** button. It never reloads by itself, since an
annotation may be in progress (upload drafts are saved; the Videos page asks
before leaving unsaved changes). Not shown on the first install.

User data (caches `data` and `media`) is deleted on logout and after each login. In
production, nginx also sends `Clear-Site-Data` on logout.

**Test it in the browser.** The service worker only runs in the production
build:

```bash
npm run build && npm run preview     # https://localhost:4173
```

Chrome refuses to register a service worker served with a self-signed
certificate, even after accepting the warning. Start a separate Chrome
profile that ignores certificate errors (only for this local test):

```bash
google-chrome --user-data-dir=/tmp/vn-chrome --ignore-certificate-errors https://localhost:4173
```

Then, in DevTools (F12) → **Application**:

- **Manifest**: name, icons, colours; warnings if something prevents installing.
- **Service workers**: status of `service-worker.js`. *Update on reload*
  avoids testing an old version; *Offline* simulates no network (reload: the
  app and the last catalogue still show).
- **Cache storage**: `shell-<version>` (app files) and `data` (catalogue per
  language, current user).
- **Storage**: usage, persistence, *Clear site data* to start over.

In **Network**, requests answered by the service worker show
"(ServiceWorker)" in the Size column. The install button appears at the right
of the address bar; **Lighthouse** checks installability. On iPhone/iPad,
install from Safari's *Share → Add to Home Screen*.

Writing tests:

- Find elements as a user does: `getByLabel('Username')`,
  `getByRole('button', { name: 'Log in' })`, not CSS classes.
- Wait with `await expect(…)` (it retries), never with fixed sleeps.
- One behaviour per test. Mocked tests for most cases; keep e2e flows few.
- TOTP codes in e2e tests are computed from the secret shown by the setup
  wizard (`otpauth`).

### 8. Uploads in development

Uploads need **tusd** (receives the files) and **ffmpeg** (encodes them). The
backend starts tusd itself when it is on `PATH` (or `VIDEONINJA_TUSD_BIN`), on
`127.0.0.1:1080`, and encodes in a background thread when `ffmpeg`/`ffprobe`
are installed; without them it logs a warning and uploads stay queued.
`npm run dev` forwards `/files` to tusd (`TUSD_URL` for another address).
Uploads and encoded videos go to `server/uploads/` and `server/media/`
(ignored by git); without nginx the app serves the thumbnails itself.

Install both first (see [Prerequisites](#prerequisites) and
[Installing tusd](#installing-tusd)), then start the backend as usual; a fast
x265 preset keeps encodings short while developing:

```bash
VIDEONINJA_DB=dev.db VIDEONINJA_DB_KEY_FILE=dev.key VIDEONINJA_X265_PRESET=ultrafast \
  uvicorn app.main:app --reload
# The log must show: "tusd started (pid …)" and "Encoder started".
```

In development `/files` reaches tusd without nginx's per-request check (see
[How uploads work](#how-uploads-work)); tusd's pre-create hook still checks the
session.

### 9. Docker image

To test the production image itself (nginx in front, the base path
`/videoninja`, the read-only container, the download limits), build it from
your checkout and run it with Docker and its Compose plugin, on the same data
as the development backend (step 2): `server/dev.db`, `server/dev.key` and the
folders `server/catalog/`, `server/media/`, `server/uploads/`.

Stop the development backend (uvicorn) first: both would encode the same
upload queue. Then:

```bash
tools/docker-dev.sh                       # build, then run (Ctrl+C stops)
# (sudo tools/docker-dev.sh if your user is not in the docker group)
```

Then open <http://localhost:8080/videoninja/> and log in with your development
users. `localhost` matters: browsers accept the session's `Secure` cookie over
plain http there only. Without `server/dev.db` (see
[Test admin without the wizard](#test-admin-without-the-wizard)) the container starts in setup
mode: the setup token is in the log (or, from another terminal:
`tools/docker-dev.sh logs server | grep "Setup token"`), and the wizard creates
`server/dev.db`, which the development backend then uses too.

What `docker-compose.dev.yaml` mounts:

| Host | Container | Used as |
|---|---|---|
| `server/` | `/data` | `VIDEONINJA_DB=/data/dev.db` (the folder, not the file: SQLite writes `dev.db-wal` and `dev.db-shm` next to it) |
| `server/dev.key` | `/run/secrets/videoninja_key` (read-only) | The encryption key, at the app's default path, like the production secret |
| `server/catalog/` | `/srv/catalog` | Catalogue snapshots (`VIDEONINJA_CATALOG_DIR`) |
| `server/media/` | `/srv/media` | Encoded videos and thumbnails (`VIDEONINJA_MEDIA_DIR`) |
| `server/uploads/` | `/srv/uploads` | tusd's uploads waiting to be encoded (`VIDEONINJA_UPLOAD_DIR`) |

- The container runs as the owner of `server/` instead of the image's UID
  10001: it can read `dev.key` (not world-readable) and the files it writes
  stay yours. The script creates the missing folders first (Docker would create
  them owned by root).
- Otherwise the production settings: read-only root filesystem, no
  capabilities, nginx on port 8080 (localhost only). Encoding uses the
  `ultrafast` preset.
- The catalogue snapshot's `current` link is relative: snapshots written by
  either side work in both.
- Any `docker compose` arguments pass through: `tools/docker-dev.sh up -d`,
  `logs -f`, `down` (stops and removes the container; the data in `server/`
  stays).
- The build uses `server/Dockerfile.dockerignore`: only the files the image
  needs are sent to Docker (no `node_modules`, databases or keys).

CI builds the same image on every push (not published).

### Database schema

The schema is designed in [drawdb](https://drawdb.app) and exported to
`server/database/db_v1.sql`. drawdb does not export `AUTOINCREMENT`: after each
export, re-add `"id" INTEGER PRIMARY KEY AUTOINCREMENT` on `video`, `segment`,
`user` and `comment`. On first start the app uses the highest
`N` for which both `db_vN.sql` and `db_vN_init.sql` exist.

Conventions: text is UTF-8 (`PRAGMA encoding = 'UTF-8'`). Dates are in columns
named `…_at` declared `DATETIME`, holding ISO 8601 text with the UTC offset in
one format, `2026-10-23T12:13:38+02:00` (`server/app/clock.py`); the API sends
them as they are. They are written in the user's timezone: the frontend sends
the browser's (`Time-Zone: Europe/Zurich`) on every API call and the app saves
it in `user.time_zone`, for writes without a browser request (tusd hooks).
Invitations and background jobs use the server's timezone (`TZ`). Offsets
differ, so the text does not sort chronologically: SQL compares and orders
dates through `datetime()` (which converts to UTC), never as plain text.
Positions inside a video stay whole seconds (`segment.begin_s`, `end_s`).

Authors: `video.uploaded_by` and `segment.created_by` (the user who added the
segment, at upload or later on the Videos page; editing a segment keeps it).
Both `ON DELETE SET NULL`. The annotation API sends display names (the user's
name, else the username), never user IDs.

`db_v1.sql` is still changed in place: there is no migration yet. A database
created before a change to it must be rebuilt (development:
`tools/make-dev-db.py --force`; production: a new setup). Since
`segment.created_by` was added, older databases fail on the Videos page and
on uploads.

Tags: a tag's name and its fixed values' names are translated (`tag.name`,
`tag_value.name`: translation IDs `tag.<id>.name`, `tag_value.<tag>.<id>.name`,
every language filled). A tag with rows in `tag_value` takes one of them
(shown sorted by name in the user's language), and `video_has_tags` /
`segment_has_tags` store that value's ID, never its name. A tag without takes
text, stored as typed and not translated, in its `value_format`: `NULL` = any
text, `year` = a year from 100 years ago to this year. Seeded (`db_v1_init.sql`):
location (outdoor, dojo), event (seminar, class, demo), year, and country (the
249 ISO 3166-1 alpha-3 codes, e.g. `CHE`, named in English and French).
Example:

```sql
INSERT INTO "translation" ("id", "en", "fr") VALUES
	('tag.place.name', 'Place', 'Lieu'),
	('tag_value.place.dojo.name', 'Dojo', 'Dojo'),
	('tag_value.place.outdoor.name', 'Outdoor', 'Extérieur');
INSERT INTO "tag" ("id", "name") VALUES ('place', 'tag.place.name');
INSERT INTO "tag_value" ("tag", "id", "name") VALUES
	('place', 'dojo', 'tag_value.place.dojo.name'),
	('place', 'outdoor', 'tag_value.place.outdoor.name');
```

## Production

One image, `videoninja`, holds the whole app: nginx (the only entry point,
plain HTTP on port 8080), the frontend, the API, tusd for uploads and the
encoding queue. The app starts and watches nginx and tusd. Your own reverse
proxy in front only handles TLS and forwards `/videoninja/` to the container:
see [6. Reverse proxy and nginx](#6-reverse-proxy-and-nginx).

The image is built in stages (`server/Dockerfile`): the frontend (Node), the
Python packages (a virtual environment), tusd and the nginx configuration
(checked with `nginx -t`) are each prepared in their own stage. The final
image only copies their results onto the runtime: Python without pip, nginx,
ffmpeg, brotli and zopfli. No build step runs in it and it holds no build tool.

Target: Raspberry Pi 5 (arm64) or any amd64 host, with Docker Engine and the
Compose plugin, Docker data on a local SSD (SQLite must not be on NFS).

**Back up the key separately from the database** (password manager, offline

### Users

**Failed logins** are throttled per client address: after 10 failed
credentials in 15 minutes (wrong password or authenticator code at login, wrong
current password in the profile, wrong setup or invitation token), that
address gets `429` on those forms until the oldest failure is 15 minutes old;
the page shows how long to wait. Other refusals (expired session, missing
access) never count. The count is in memory: restarting the container resets
it. Users sharing one address (a club's Wi-Fi) share the count; an attack from
many addresses is not stopped by it, the authenticator code still is. The
address is your proxy's `X-Forwarded-For`: if the proxy does not set it, every
client looks the same and one attacker throttles everybody.

Users are added by invitation, from **User Management** in the user menu
(top right; only for roles with the `user_mgmt` access, i.e. admins):

1. Enter a username, choose a role, click **Create**. The app shows an
   invitation link (`https://<host>/register#<token>`), valid for **one week**,
   and copies it to the clipboard. Send it to the user.
2. The user opens the link and chooses a display name (optional), a password
   and an authenticator app. The link then stops working.

In the user list, the first column shows the state: a green check
(registered), nothing (invitation pending: the copy button gives the link
again) or a red cross (invitation expired). The reset button issues a new
link. For a registered user, reset also removes the password and
authenticator and logs the user out: that is how a lost password or
authenticator is recovered. Every user must use an authenticator app; there
is no way to log in without one. Admins cannot reset their own account.

Roles and what they allow (accesses):

| Role | `segment` | `comment` | `annotate` | `upload` | `video_mgmt` | `user_mgmt` |
|---|---|---|---|---|---|---|
| `user` | ✓ | ✓ | | | | |
| `editor` | ✓ | ✓ | ✓ | | | |
| `uploader` | ✓ | ✓ | ✓ | ✓ | | |
| `video_mgmt` | ✓ | ✓ | ✓ | ✓ | ✓ | |
| `admin` | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

**Videos** (top menu, right of Upload; `video_mgmt` access) lists every
published video in four collapsible sections: **In progress** (some
techniques, not all), **To annotate** (none yet), **Complete**, and **No
technique** (marked as containing none). Each thumbnail shows the video's
duration and whether it is saved on this device.
A video opened here is saved on the device by the PWA, like clips (deleted
on logout): reopening it doesn't download it again. Clicking one opens the same annotation panel as the upload page,
with the video from the server and its saved segments and tags: **Proceed**
saves them (nothing is uploaded). Segments keep their ID; new or re-timed ones
get a new thumbnail, and the PWA drops saved clips of segments re-timed or
removed when it gets the new catalogue.

**Comments:** on a technique's page, **Add a comment** (with the `comment`
access) opens a form for the text and its language (the interface's by
default). Comments show the author, the language (flag) and the time of the
last change ("(edited)" once changed), last changed first. Each user edits and
deletes only their own comments, admins included: nobody can change someone
else's.

to the server: it does not appear in nginx logs or `Referer` headers.

### Uploading videos

**Upload** (top menu, right of Schools) is shown to roles with the `upload`
access (uploaders and admins):

1. Choose a video file. It is opened on the device, not sent: its SHA-256 is
   computed and checked: "This video already exists" if it is the original
   of a video already uploaded, or the published file of one.
2. Play it, step frame by frame (⏮ ⏭ or ← →), and mark technique segments:
   drag across the film strip, or **Begin here (I)** / **End here (O)** at the
   current frame; drag a segment's edges to adjust it. Pointing at the film
   strip (also while dragging) shows that frame without moving the playhead;
   click to move it there. For each segment choose
   school › level › technique and the performer (or add one), and optional tags.
3. Or choose **Define segments later** (the "all segments done" box is then
   off) or **This video does not contain any technique segment** (box on).
4. **Proceed** uploads the original (resumable, 50 MB at a time) with the
   segments. The video then waits in the server's queue; **My uploads** shows
   its place, the encoding progress, and Retry/Delete if it failed. It appears
   on the technique pages once encoded. The page can be left at any time.

Unfinished work is kept on the device and resumed by choosing the same file
again (until logout). A file the browser cannot play (some AVI/DV/MPEG-2, or
H.265 in Firefox) can still be sent with "Define segments later".

Encoding happens on the Pi, one video at a time, in software: a 1080p video
takes roughly as long as several times its duration with the `medium` preset
(measure on your Pi; `VIDEONINJA_X265_PRESET=fast` halves it). Interlaced
sources are deinterlaced (NNEDI3) and HDR ones tone-mapped, as by
`tools/encode-videos/encode-videos.sh`. A file already in that format (e.g.
encoded with the script before uploading) is not encoded: its video and audio
are copied into a new file (seconds, no quality lost). Only the format counts:
MP4 with faststart, one H.265 Main 8-bit `hvc1` video, SDR BT.709,
progressive, a keyframe every second, AAC mono or stereo (one audio stream) or
no audio.

Published videos never keep their metadata: tags (a phone's GPS location,
dates, device, title), chapters and other streams (data or GPS tracks,
timecode, subtitles) are removed, whether the video was encoded or only
copied. The picture's rotation (portrait videos) is kept. The published file
is therefore never byte for byte the original: both hashes are kept, and a
new upload of either is refused. The original is deleted once the video is
published; an upload not submitted within a week is deleted too.

`encode-videos.sh` used by hand (to encode before uploading) also removes the
metadata; `-m` keeps it (the server removes it anyway when publishing). Mono
audio stays mono; more than two channels are mixed down to stereo.

### 6. Reverse proxy and nginx

Two nginx: **your reverse proxy** (TLS, your domain, the `/videoninja/`
subfolder) and **the container's nginx** (everything else, configured by the
image). Your proxy only forwards; it needs no modules beyond the standard ones.

#### Your reverse proxy

In the `server` block that already serves `https://example.org` with TLS:

```nginx
# HSTS for the whole domain: here, not in the app (a subfolder must not decide
# for the domain). Add includeSubDomains only if every subdomain has HTTPS.
add_header Strict-Transport-Security "max-age=31536000" always;

location = /videoninja {
    return 301 /videoninja/;
}

location /videoninja/ {
    # No URI after the address: /videoninja/… is forwarded unchanged (the
    # container serves under /videoninja/).
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Connection        "";
    proxy_set_header Host              $host;
    # The container builds upload URLs from these (https, your domain and port).
    proxy_set_header X-Forwarded-Host  $http_host;
    proxy_set_header X-Forwarded-Proto $scheme;
    # Overwrite, never append ($proxy_add_x_forwarded_for): the container
    # trusts this single value as the client's address.
    proxy_set_header X-Forwarded-For   $remote_addr;

    # Uploads: 50 MB chunks, streamed to the container (no temporary copy),
    # with time for a slow link.
    client_max_body_size    64m;
    proxy_request_buffering off;
    proxy_read_timeout      300s;
    proxy_send_timeout      300s;
    # Pass answers on as they come: the setup wizard's progress, video.
    proxy_buffering off;
}
```

Check, then reload: `sudo nginx -t && sudo nginx -s reload`. The other sites
of the domain are not affected; the `add_header` line applies to the whole
`server` block (if a `location` there has its own `add_header`, repeat it
there: nginx does not merge them).

Then check from outside:

```bash
curl -sI https://example.org/videoninja/ | grep -iE '^(HTTP|content-type|strict-transport)'
# HTTP/2 200, content-type: text/html; charset=utf-8, strict-transport-security: …
curl -s https://example.org/videoninja/health      # {"status":"ok"}
```

#### Sharing the domain (subfolder)

Under a subfolder, Video Ninja has the same **origin** (`https://example.org`)
as everything else on the domain, and browsers isolate by origin, not by
path. Accepted for this setup, with these consequences and mitigations:

- Pages of the domain's other sites can read Video Ninja's browser storage
  (cached catalogue, clips, upload drafts) and call its API with the user's
  cookie: an XSS in any of them reaches Video Ninja. CSP `'self'` covers the
  whole origin too.
- The session cookie is limited to the app: `__Secure-session` with
  `Path=/videoninja` (at the domain's root it is `__Host-session`, `Path=/`).
  The other sites' servers never receive it.
- Logout sends `Clear-Site-Data: "cache", "storage"`, which clears the
  browser's cache and storage **for the whole origin**, so also for the
  domain's other sites (logged-in state kept in their local storage, their
  offline data).
- HSTS comes from your proxy, for the domain.

A subdomain (`videoninja.example.org`) isolates the app completely: build the
image with `BASE_PATH=` (empty) and proxy the whole subdomain to it.

#### nginx in the container

[`nginx/nginx.conf`](nginx/nginx.conf), started and restarted by the app
(`server/app/nginx.py`), runs as the container's user, writes only to `/tmp`,
and logs through the app (`docker compose logs`). It:

- serves the frontend (the SvelteKit build in `/srv/www/videoninja/`) with its
  precompressed `.br`/`.gz` files and the caching headers (hashed files
  forever, the rest revalidated);
- removes the base path and proxies `/videoninja/api/` and `/videoninja/media/`
  to the app on the container's loopback (`127.0.0.1:8000`);
- serves catalogue and media after the app's `X-Accel-Redirect` (below);
- checks every upload request with the app (`auth_request`) before tusd
  (`127.0.0.1:1080`) gets it;
- sends the security headers (CSP, `Referrer-Policy: no-referrer`, …) and
  takes the client's address from `X-Forwarded-For`, trusted only from
  private addresses (your proxy);
- sends **one clip per user at a time** (whole videos on the Videos page: four
  transfers per user, its own count: the editor's three video elements and the
  download that saves the video on the device). The app puts the user's ID in the
  internal redirect (`/protected-clip/<user id>/…`, `/protected-video/<user id>/…`)
  and nginx counts the transfers in progress (`limit_conn`): a second one gets
  `429`, and the player says that another video is still downloading (a clip
  being saved for offline use counts too). A transfer ends when the file is
  sent or the browser goes away. Thumbnails are not limited. Without nginx
  (development) there is no limit.

The app and tusd listen on the container's loopback only: nginx is the only
way in. The modules come from Debian's `nginx` package (`mp4`,
`auth_request`, `gzip_static`, `realip`) and `libnginx-mod-http-brotli-static`.
The image runs `nginx -t` on the configuration when it is built. The
configuration is written for `/videoninja/`; the `BASE_PATH` build argument
rewrites it (and builds the frontend) for another path.

Every `add_header` is set once, in the `server` block, with per-path values
from `map`s: nginx drops all inherited `add_header`s in a location that has
its own, so no location has any.

#### Compression: precompressed only

nginx never compresses at request time (`gzip off`). Every compressible file is
compressed once, when it is written, and nginx picks the variant that matches
the browser's `Accept-Encoding` (`brotli_static` / `gzip_static`, with
`Vary: Accept-Encoding`):

| File | Written by | Variants |
|---|---|---|
| `catalog.<lang>.<hash>.json`, `annotations/<id>.<hash>.json` | the app, on each snapshot | `.br` (`brotli -q 11`), `.gz` (Zopfli) |
| `/_app/immutable/*`, `index.html`, `service-worker.js` | `npm run build` (`precompress: true` in adapter-static) | `.br`, `.gz` |
| Videos, thumbnails, filmstrips | — | none: already compressed |

Brotli at maximum level is slow but runs only when the catalogue changes, and
is typically 15–25 % smaller than gzip on JSON. Zopfli writes standard gzip
files about 5 % smaller than `gzip -9`, as the fallback. Zstandard and
Compression Dictionary Transport are not used: no reliable Safari support, and
ETag + `304` already makes updates cheap.

Check, through nginx with a valid session cookie:

```bash
curl -sI -H 'Accept-Encoding: br' -b '__Secure-session=…' https://example.org/videoninja/api/catalog \
  | grep -iE 'content-encoding|vary|etag'
# Content-Encoding: br, Vary: Accept-Encoding, ETag: "…"
```

#### Catalogue updates

- The app writes the snapshot in `/srv/catalog`:
  `versions/<version>/catalog.<lang>.<hash>.json` with its `.br` and `.gz`,
  and a `manifest.json`; `current` is a symlink to the latest version,
  swapped atomically. A version is never changed once written.
- It is rebuilt at startup, after setup, and after every write that changes
  the catalogue, whoever makes it (admins, editors, uploaders…), debounced
  (2 s): a burst of edits makes one rebuild. An unchanged catalogue makes no
  new version, so the ETag stays the same and clients keep getting `304`.
  The 3 previous versions are kept for requests in flight, older ones deleted.
- `/api/catalog` (session check, then `X-Accel-Redirect` to
  `/protected-catalog/<version>/catalog.<lang>.<hash>.json`) has a stable URL
  and is served `private, no-cache` with an ETag. It must not be `no-store`:
  the browser keeps it and revalidates with `If-None-Match`.
- The service worker uses stale-while-revalidate: it shows the cached
  catalogue at once and revalidates in the background, usually getting a
  `304` of a few bytes.
- A few thousand segments is a few hundred KB of JSON, typically under 100 KB
  compressed. Past roughly 1–2 MB compressed, split it by school
  (`catalog.<ryu>.<lang>.<hash>.json` plus a small index file), still as
  pre-generated static files.

#### How media access works

Media and catalogue files are served with **`X-Accel-Redirect`**:

1. The browser requests `/videoninja/media/segment/42` (with its session
   cookie; browsers send cookies on `<video>` requests). Thumbnails:
   `/videoninja/media/segment/42/thumbnail`.
2. nginx proxies it to the app (as `/media/segment/42`). The app checks the session, looks up the
   segment and computes start/end itself.
3. The app answers with an empty body and
   `X-Accel-Redirect: /protected/ab/<sha256>/video.mp4?start=12&end=27`, or
   `401`/`403`/`404`.
4. nginx serves the file from an `internal` location. With `start`/`end`, the
   `mp4` module returns a valid standalone MP4 for just that range: it rebuilds
   the index (`moov` atom) and streams the relevant bytes, with no transcoding.
   The index comes first, so the clip plays while the rest downloads; it
   starts on the keyframe at or before `start` (one every second).

Without nginx (development), the app cuts each clip once itself, with
`ffmpeg -c copy` (same keyframe rule), into `server/media/clips/`, and serves
it with `Range` support.

The `Range` header survives the internal redirect, so every seek is a
`206 Partial Content` from nginx, and every seek goes through the app check
again. The mp4 output is deterministic (same file, same start/end, same
bytes), so successive range requests fit together.

Alternatives considered:
- `auth_request`: also one app call per request, but the app cannot choose
  the file or the range; the client would have to send them.
- `secure_link`: nginx checks an HMAC itself, with no app call per seek, which
  is the lightest option for a Pi. If used, the signed string must include the
  range (`$secure_link_expires$uri$arg_start$arg_end secret`) so nobody can
  widen it. **Not used for now:** a signed link stays valid after logout,
  session expiry or account removal until it expires, which breaks the rule
  that the app decides on every request. The per-seek cost of
  `X-Accel-Redirect` is one SQLite lookup, small at this scale.

#### How uploads work

Large files go to **tusd** (run by the app in its container, restarted if it
stops) with the tus protocol: the browser creates the
upload, then sends it in 50 MB chunks (`PATCH`), each a bounded, retryable
request; after an interruption it asks for the offset (`HEAD`) and continues.

- **Every** request to `/videoninja/files/` is first checked by the app with
  `auth_request` (session, `upload` access, and the upload is the user's own),
  so the app decides on each chunk, as for media. tusd's `pre-create` hook
  checks again and names the upload; `post-finish` marks it complete.
- nginx streams the chunks to tusd (`proxy_request_buffering off`): no
  temporary copy on the Pi. `client_max_body_size 64m` is one chunk;
  the file size is limited by tusd (`-max-size`) and the app
  (`VIDEONINJA_MAX_UPLOAD_GB`).
- tusd runs with `-disable-download`: uploads cannot be read back.
- The app's encoding thread takes the oldest queued video, checks the original
  (complete, SHA-256 as announced), encodes it with `encode-videos.sh` at low
  priority, writes `video/<h2>/<sha256>/{video.mp4, thumb.jpg,
  segment-<id>.jpg}` and publishes it. A restart puts an interrupted encoding
  back in the queue (3 tries at most; a clean stop does not count as a try).

#### Frontend side of the contract

- **Range requests from the cache:** a clip played from the Cache API needs
  proper `206 Partial Content` answers, or seeking and even playback break
  (Safari in particular). The service worker answers them from the saved clip
  (`src/service-worker/range.ts`). Clips are saved **without** a `Range`
  header, so that the full `200` response is stored.
- **Cookie:** `__Secure-session` with `Path=/videoninja` under a subfolder
  (`__Host-session`, `Path=/` at the domain's root), `HttpOnly; Secure;
  SameSite=Strict`. Works with `<video>`, since browsers send cookies on
  same-origin media requests.
- **Audit trail:** nginx logs the final status of every request (`401`/`403` =
  denied); the app logs each allow/deny decision with user and segment ID.
